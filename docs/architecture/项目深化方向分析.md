# 项目深化方向分析

分析日期：2026-11-09。代码基线：`df6d7e4`。本文是下一阶段建议，不表示候选能力已经实现或已决定全部开发。

## 1. 建议主线

围绕“理解当前项目、记得项目决策、能持续协作的个人助手”深入，第一步交付带来源的项目资料问答。

最有价值的变化是：用户在项目中提问“这个项目怎么启动、为什么采用这套架构、接下来做什么”，助手能依据用户选定的真实文件回答，指出来源与信息缺口；新建项目会话时可以沿用已确认的项目说明和决策。后续再把回答转成可确认、可验证的执行任务。

这一方向能把最近完成的 Windows 桌面项目入口，与既有知识、写作和执行能力连接起来。通用聊天仍是基础能力；近期投入集中在减少用户反复粘贴资料和重复解释项目背景。

## 3. 可以深入的方向及排序

投入为相对估计，不是工期承诺。

| 优先级 | 方向 | 用户收益与技术深度 | 相对投入 | 进入条件 |
| --- | --- | --- | --- | --- |
| P0 | 长对话正确性与上下文管理 | 最新问题始终入模；历史展示与请求组装分离；限制输入体积，保留有效上下文 | 小到中 | 立即作为基础修补 |
| P1 | 项目资料问答与来源追踪 | 选定 README、设计说明或代码片段后直接提问；回答可回查文件版本和行号 | 中 | 第一条产品主线 |
| P2 | 可管理的项目记忆 | 跨会话复用用户确认的目标、约束、决定和待办；可编辑、删除、查看来源 | 中 | 项目问答已有人实际使用 |
| P3 | 联网研究与技术写作 | 查询官方资料、核对时效、结合项目背景形成方案或文章 | 中到大 | 已有具体的外部资料需求 |
| P4 | 桌面任务执行闭环 | 从分析进入修改、验证和结果交付；展示进度、取消、等待与恢复 | 大 | 明确复用 Python 执行内核的接入方式 |
| 并行支撑 | 结果评测与桌面回归 | 能回答“实际是否更有用、有没有错误引用、慢在哪” | 首期小，持续积累 | 随每个切片建设 |

### 3.1 P0：先处理已确认的长对话问题

`ChatStore::messages()` 固定调用 `messages_page(session_id, 0, 500)`，SQL 按 `rowid` 正序读取。前端历史展示与 `desktop_chat_send` 请求历史共用此方法。

因此，当会话总消息数超过 500 条，最新消息会落在读取窗口之外。发送流程先落库用户提问，再读取该窗口，存在新问题已保存却没有送给模型的情况。前端刷新也只显示最早 500 条。

本轮用源码中的同一条 SQL 在内存 SQLite 插入 501 条合成消息：返回第 1～500 条，第 501 条用户提问未返回。此复现不调用模型、不读取真实聊天库；尚未修复业务代码。

建议将三件事分开：

1. 历史展示：默认显示最近一页，可继续加载更早历史。
2. 模型输入：保留当前问题与最近完整轮次，在明确的输入预算内选择历史及项目材料。
3. 长期压缩：后续再引入可追溯摘要，保留对应消息范围、版本和生成状态，避免摘要静默覆盖原始记录。

第一步无需模型摘要即可修复窗口错误。消息条数不能替代上下文长度预算；即使不足 500 条，长消息也可能超过模型输入限制。

### 3.2 P1：从选定材料开始做项目理解

首期让用户在项目中明确选择少量文本文件，预览将被使用的内容，再围绕这些材料提问。先完成“材料进入请求—有依据回答—来源回查—重启后仍可追溯”的闭环。

建议保存来源相对路径、内容指纹、行范围和本轮实际使用的文本快照。文件后来变化时，旧回答仍能显示当时依据，同时提示与当前版本的差异。回答里出现合法引用 ID 不等于语义正确，仍需抽查其是否支撑结论。

首期不需要全目录自动索引或向量库：少量明确材料即可检验用户是否持续使用。材料多到超出上下文后，再依据真实问题引入现有检索能力。项目文档作为参考数据处理，不能因为文件里写了指令就改变助手权限。

目录绑定仍然只表示项目归类。新增文件功能需要独立、可见的选材动作；本地材料会发送给当前模型服务这一点应在选材时说明。实现需处理路径越界、链接目标、二进制与大文件，并在发送前固定材料和项目版本，避免切换项目或移动会话导致背景串用。

### 3.3 P2：先沉淀项目决定，再扩展个人记忆

优先记录“为什么这样做”和“接下来做什么”：项目目标、技术约束、已确认决定、未解决问题、下一步。每条记录包含作用范围、来源和更新时间，用户可以直接修改和删除。

先由用户明确保存，后续再让模型提出待确认的记忆建议。聊天摘要、项目事实和用户偏好分别管理；同项目会话共享资料不代表自动共享全部对话。资料更新或决定被撤销时，旧记录需要标记失效。

这一步的价值指标是新会话开始时需要重复解释多少背景，以及是否出现过期决定干扰回答，而不是记忆库条目数量。

### 3.4 P3：联网研究服务于具体问题

典型任务：“对照当前项目依赖和官方文档，评估两种实现方案，给出引用和适用条件。”需要真实搜索服务、正文读取、来源与时间记录，才能从结果摘要走向可靠研究。

优先复用既有写作流程的研究、提纲确认和草稿产物能力。评价最终结论、引用支撑与时效；私有项目事实仍以选定本地材料为准。这个方向有价值，但应避免与项目资料首期同时铺开。

### 3.5 P4：在已有内核上接通执行

更深的执行任务可以是“依据项目约定修改一个小功能，运行指定验证，解释差异”。已有 Python Worker、Run、操作记录、恢复与测试报告适合作为接入基础。

接入顺序建议为：只读分析任务 → 在桌面查看真实任务事件与结果 → 一个边界明确的修改/验证任务。进度来自实际事件，完成来自产物与验证结果；不以模型说“完成”代替执行事实。

当前统一 Runtime 有明确的冻结范围。执行方向应另作增量设计，继承现有未知操作等待核查的行为；本分析不把通用副作用改造、宿主 shell 或新的恢复保证列为当前版本必须补齐的门槛。

## 4. 架构建议：按能力连接两端

短期保留原生普通聊天入口，在 Rust 侧仅增加简单的选材、文本快照与请求上下文组装；不为这个切片启动完整 Python 服务。这样能延续现有不依赖 WSL 的使用体验。

在联网研究或多步执行进入开发前，先明确能力边界：桌面负责交互、Windows 文件/凭据与连接；复杂编排优先复用 Python 助手内核。避免在 Rust 中重做另一套完整 Agent、RAG、任务恢复和预算系统。

接入时必须显式处理桌面项目 ID 到后端工作区的映射、Windows/WSL 文件可达性、请求与事件关联、取消和凭据归属。Windows 原生目录并不天然等于 Python 后端可访问且已授权的工作区。

第一轮不用合并两套数据库。共享的重点是材料、来源、请求和结果的契约；未来接入任务时，明确任务历史由谁保存、桌面保存什么关联信息。若复杂任务变成主要使用场景，再依据实际维护成本评估运行时收敛。

## 5. 下一轮可直接拆出的工作

推荐交付目标：在一个桌面项目中选取 README 和一份设计说明，询问项目结构与下一步，得到可回查来源的回答；长会话中最新问题正常入模，重启后材料记录与回答保持一致。

按依赖顺序推进：

1. **修复历史与输入窗口。** 区分展示分页与请求历史，保留最新提问，建立输入预算和超限反馈。
2. **加入明确的项目材料。** 选择、预览、移除文本文件；保存版本与本轮快照；请求发送前固定项目及材料集合。
3. **展示依据。** 支持来源回查与版本变化提示，区分材料支持的事实、推断与未知项；补齐基础 Markdown/代码块显示。
4. **同步建立回归。** 现有前端测试之外，补上原生存储/上下文测试及 chat-mode 构建入口；用少量真实使用任务评价效果。

首轮建议保留以下验收案例：

| 案例 | 应看到的结果 |
| --- | --- |
| 普通独立聊天 | 没有项目材料也能正常对话 |
| 500 条以上历史后继续提问 | 最新问题与相关近期轮次进入请求；历史能加载最新内容 |
| 长文本与材料超限 | 明确说明取舍或要求缩小材料，避免无提示地丢掉当前问题 |
| 两个项目包含矛盾配置 | 回答只使用当前选定材料，切换/移动会话不串用背景 |
| 文件变更、删除或移出目录 | 旧回答可追溯当时版本；新请求明确提示材料状态 |
| 材料不含所问事实 | 说明缺口，通用知识或推断有明确标识，不编造项目事实 |
| 材料包含指令式文本 | 文档内容不能改变权限或触发额外文件访问 |
| 取消、请求失败及重启 | 不把部分输出保存为完整成功；已保存来源与回答对应一致 |

首期以人工判断正确性、来源支撑和背景串用为主；同时记录首字延迟、端到端耗时和输入体积。模型未报告用量时记为未知。已有 `MinimalResultEvaluator` 可复用作结构、证据和约束检查，但不能代替人工语义判断，也不能不经适配直接当作原生聊天验收器。

## 6. 暂后排序与重新评估条件

- RAG 算法专项：沿用转维护决定；实际项目材料规模或检索失败证明有需要时再投入。
- 完整多 Agent、插件平台、分布式 Worker：当前主要问题是能力没有进入日常使用闭环，尚缺引入这些复杂度的证据。
- 移动端、语音与虚拟形象：保留为未来产品方向；项目协作形成稳定价值后再扩展入口和表现形式。
- 自动跨会话记忆与主动调度：在可管理记忆和任务生命周期成熟后推进，先解决记录是否正确、是否过期及如何撤销。

若实际主要需求是公开资料研究，可把 P3 提前；若目标变为工程架构展示，可把事件可观测性与结果评测提前。默认推荐仍是 P0 → P1 → P2，随后按实际任务选择研究或执行。
