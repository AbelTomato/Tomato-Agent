# SQLite 持久化执行内核实施计划（计划日期：2026-10-10）

> **执行要求：** 使用 `executing-plans` 按任务顺序实施；涉及核心执行行为时使用测试优先流程。每个任务先验证失败测试，再实现和运行目标测试。当前任务 1～6 已完成目标验证。未经用户明确批准，不执行 Git 写操作、真实 Provider/Sandbox 调用或业务数据库迁移。

**目标：** 为受控代码任务建立单机 SQLite 最小执行内核，支持持久化领取、租约接管、步骤恢复、预算延续、过期执行者提交拒绝和可查询的恢复轨迹。

**架构：** 保留现有 `task_runs`、事件、checkpoint 和业务验收逻辑，新增 Attempt、逻辑 Operation 与执行 Step。执行内核统一管理短事务与恢复决策；Harness 通过可选执行端口保存消息、预算和下一动作；现有非持久化 Harness 行为保持不变。

**技术栈：** Python ≥ 3.11、Pydantic 2、SQLite/aiosqlite、pytest、pytest-asyncio、asyncio 和标准库 subprocess；不新增第三方依赖。

**规格依据：** 本轮已确认的 SQLite + 显式状态机 + 租约 + 操作日志/trace 首版方向，以及以下项目文档：

## 一、范围与约束

- 在主工作树 `仓库根目录` 实施，保留已有改动，不创建分支/worktree。
- 首版只接入固定 fixture 的代码任务；不改造对话 Runtime 和写作执行器。
- 保持同步 execute API；新增显式 recover 入口，不启动自动后台调度。允许受控双进程竞争实验，不宣称多机或生产多 Worker 可用。
- 不引入 Redis、Celery、PostgreSQL、Temporal、任意 shell 或新的真实外部资源。
- 执行表与 `task_runs` 使用同一 SQLite 文件，才能原子更新；复用现有配置路径，不新增独立业务库。
- 开发及故障注入只使用独立测试数据库/workspace；禁止直接操作现有业务数据。持久报告放在 `backend/data/execution-recovery/`，不提交生成产物。
- 首版保证数据库提交隔离，不保证任意外部副作用 exactly-once、零重复模型费用或跨文件原子写入。
- 不新增独立 trace 表：扩展现有 `task_run_events` 的事件 payload，避免同一事件两份存储。恢复权威来自操作状态和快照，不从 trace 文本推断执行事实。
- 已终态 Run 不复活；未知副作用进入 `waiting` 并标记原因。等待释放租约；人工等待不等同于可自动重试。
- 历史 Run 没有 v1 快照时只允许查询和取消，不自动恢复；新的持久化执行适配不得偷偷把历史 running Run 当作新任务。

## 二、现状与设计修正

当前 `RunRepository` 有合法迁移、版本控制和逐操作事务，但没有执行所有权，事件/checkpoint/终态分开提交。checkpoint 的 sequence 表示保存次数，不是事件游标。

`CodeTaskService.create()` 会立刻把 Run 标为 running；`execute()` 使用内存集合去重，并创建全新的 HarnessState。Harness 的消息、模型/工具计数和耗时在内存中，已有测试结果 checkpoint 不能支持完整续跑。

首版作以下修正：

1. 新 Run 创建后保持 queued，领取成功才进入 running；这是公开行为变化，需回填 API 文档和测试。
2. Attempt 每次领取都新建，不覆盖旧 Attempt。fencing token 在 Run 范围内单调递增，不在每个 Attempt 从 1 开始。
3. Operation 表示一个稳定的逻辑调用；Step 表示一次实际调用尝试。接管可保留 Operation，但为重试创建新 Step。
4. 内核提供受令牌保护的原子提交接口；旧 `RunRepository.update_status/save_checkpoint/append_event` 不能用于新持久化执行路径绕过所有权。
5. 完整快照包含消息和待执行动作；仅保存 step index、摘要和 artifact 引用不够恢复模型上下文。
6. 租约失效不能撤销已经发出的文件/Sandbox 操作。未确认旧进程退出时，未知写入或 Sandbox 不自动接管执行；先进入 waiting，阻止两个执行者并发写同一 workspace。

## 三、模型与状态机

### 数据表

| 表 | 最小字段和约束 |
| --- | --- |
| `execution_run_heads` | run_id 主键/FK、active_attempt_id、fencing_token（非负且每次领取 +1）、cancel_requested、protocol_version；一 Run 一行 |
| `execution_attempts` | id、run_id、attempt_no、owner_id、fencing_token、status、lease_expires_at、heartbeat_at、started_at、finished_at、error_code；UNIQUE(run_id, attempt_no)、UNIQUE(run_id, fencing_token) |
| `execution_operations` | id、run_id、logical_index、kind、tool_name、input_digest、input_payload、recovery_class、status、result_payload/result_ref；UNIQUE(run_id, logical_index) |
| `execution_steps` | id、operation_id、attempt_id、execution_no、status、started_at、finished_at、error_code、output_digest；UNIQUE(operation_id, execution_no) |

采用 JSON 存储经过 schema 校验的数据；禁止 pickle。建立租约扫描索引 `(status, lease_expires_at)`、Run 查询索引和操作状态索引。新表初始化采用可重复的版本化迁移，不改写旧 checkpoint 格式，不靠 CREATE TABLE 的存在冒充迁移完成。

Attempt 状态采用最小集合：`running → succeeded | failed | cancelled | expired | released`。创建 Attempt 与取得租约在一个事务内完成，故无需持久化 claimed/queued 中间态。released 表示进入等待并放弃执行权；expired 表示失联，不代表操作失败。

Operation 状态：`prepared → running → succeeded | failed | unknown`；unknown 经核对可转 succeeded，或经安全重试决策转 prepared，或保持 unknown 等待人工。Step 状态：`running → succeeded | failed | unknown`；不把旧 Step 改回 running，重试新建 Step。

Run 继续使用已有状态。受控恢复新增 `running → queued`，仅允许恢复事务在租约过期、安全判定后使用；waiting 经获准恢复可重新领取进入 running。禁止调用普通更新接口实现此迁移。completed/failed/cancelled/timed_out 仍是终态。

### 操作标识

operation_id 在模型结果持久化时生成并保存，此后恢复沿用；稳定性来自持久化记录，不依赖重新生成模型 tool_call_id。输入摘要使用标准库 SHA-256 和规范化 JSON（sort_keys、固定 separators、UTF-8）；同一 logical_index 输入摘要不一致时返回 `operation_input_conflict`，不覆盖旧记录。

### Trace

复用 `task_run_events`，payload 增加 attempt_id、operation_id、step_id、fencing_token、reason_code。事件类型为 `execution.claimed/expired/recovered/lease_rejected`、`operation.prepared`、`step.started/succeeded/failed/unknown/reconciled` 和 `execution.waiting/completed/cancelled`。

拒绝旧提交时，只能追加明确标记为拒绝的审计事件，不能附带修改 checkpoint 或业务状态。心跳不逐次落事件，避免无意义写放大；记录领取、失联、恢复和拒绝即可。错误使用稳定代码，原始异常、凭据和完整文件不进普通事件。

## 四、租约、事务与恢复快照

### 租约

- 使用 `BEGIN IMMEDIATE` 和短事务领取；读取当前 head、验证 Run/租约、递增 Run token、新建 Attempt、更新 head/Run、追加事件，然后一起提交。
- 默认租约 30 秒、心跳 10 秒，配置要求 lease_seconds > 2 × heartbeat_seconds；每次操作验证实际剩余租约。测试注入 Clock，不依赖长时间 sleep。
- 同一事务使用同一个 UTC 时间值；持久过期判断使用 UTC，单进程耗时用 monotonic。首版假设单机时钟正常，记录时钟跳变限制。
- heartbeat 和所有提交要求 active_attempt_id、owner_id、fencing_token 匹配、未取消、租约未过期。过期租约禁止续活，必须新建 Attempt。
- 每个连接启用 foreign_keys、明确 busy_timeout；仅为执行库初始化配置 WAL，采用明确同步策略并测试。数据库锁忙与业务所有权冲突使用不同错误码。外部 I/O 不放在 SQL 事务内。

### checkpoint v1

继续写 `task_run_checkpoints.state`，至少包含：protocol_version、schema_version、checkpoint_revision、last_event_sequence、phase、logical_index、messages、HarnessState、pending_operation_id、pending_response、budget_limits、reserved_model_calls、reserved_tool_calls、loop_count、elapsed_upper_bound_seconds、policy_digest、workspace_id、test_results 和 artifact_ids。

phase 为 `ready_model/pending_tool/ready_finish/waiting`。messages 使用现有 Message JSON schema，并按已有上下文策略压缩；输入参数及消息属于受控恢复数据，不等于公开 trace。凭据不进入消息/参数，敏感字段遇到不可逆脱敏时拒绝作为可恢复输入，不用 `[REDACTED]` 代替原参数继续执行。

模型调用之前原子预留模型/loop 预算，工具调用之前预留工具预算；失败、超时和崩溃也不退还调用次数。调用成功但结果未持久化时模型允许重试，消耗新预算；不承诺复用丢失的模型响应或准确计费。

耗时保存累计值和 in-flight 起始时间/最大耗时。崩溃后按该调用预留上限保守扣减，防止无限恢复重置耗时；等待人工不计执行时间。达到任一预算直接终止，不继续外部调用。

### 原子接口

以下接口均为异步，模型类型定义在 execution/models.py；run_id/attempt_id/operation_id 使用 UUID，owner_id 使用 str。

```text
init() -> None
claim(run_id, owner_id, lease_seconds) -> LeaseHandle
heartbeat(lease: LeaseHandle, lease_seconds) -> LeaseHandle
get_snapshot(run_id) -> ExecutionSnapshot | None
prepare_operation(lease, operation: OperationInput, snapshot) -> OperationRecord
start_step(lease, operation_id, snapshot) -> StepRecord
commit_step(lease, step_id, result: StepOutcome, snapshot) -> ExecutionSnapshot
commit_model_response(lease, response: LLMResponse, snapshot) -> ExecutionSnapshot
finish(lease, outcome: RunOutcome, snapshot) -> RunRecord
request_cancel(run_id) -> RunRecord
scan_expired(limit: int) -> list[AttemptRecord]
expire_and_classify(attempt_id) -> RecoveryCandidate
apply_recovery(candidate, decision: RecoveryDecision) -> RunRecord
```

LeaseHandle 包含 run_id、attempt_id、owner_id、fencing_token。模型/工具提交统一在事务内验证 handle，写操作/步骤、事件、checkpoint 和必要 Run 状态；last_event_sequence 记录该事务最后事件。未知 ID 使用明确 not-found 错误，令牌/租约失效统一 `stale_execution_owner`，非法迁移为 `invalid_transition`。

request_cancel 原子记录取消意图、失效 token 并将 Run 置 cancelled，使并发完成无法覆盖；Sandbox 清理结果独立记录，业务 cancelled 不表示外部资源已清理。正常完成先提交时，随后取消幂等返回 completed。

## 五、恢复规则

| 情况 | 首版决策 |
| --- | --- |
| Operation 已成功且摘要匹配 | 复用持久结果，不执行工具 |
| 未提交的模型调用 | 丢弃未持久结果，在剩余预算内重试；已持久响应直接继续 pending_tool |
| 只读工具运行中失联 | 旧 Step 标 unknown，新 Step 重试；结果不保证来自同一文件快照 |
| 文件写入/补丁结果未知 | waiting/manual_review；核对前后 SHA-256，必须确认旧执行者退出才允许继续 |
| 文件结果等于全部预期后像 | 确认无旧执行者后 reconcile 成功；不再次应用补丁 |
| 文件等于全部前像 | 确认无旧执行者后允许重试；部分修改或第三种内容保持 waiting |
| Artifact 创建结果未知 | 按持久化 operation_id 和内容摘要核对，找到唯一结果才复用；否则 waiting |
| Sandbox 测试执行中失联 | waiting；先核对/清理明确归属资源，再允许显式重试并累计预算 |
| 未知协议、policy 不匹配、快照缺字段 | 拒绝恢复，保持可查询状态，返回稳定错误码 |

首版只读与模型边界自动分类为可恢复；不自动批量清理 Sandbox，不实现复杂文件回滚。人工恢复要求显式确认执行者退出/资源核对事实，记录原因和结果摘要；确认接口不允许提交任意 SQL、文件内容或放宽 policy。
