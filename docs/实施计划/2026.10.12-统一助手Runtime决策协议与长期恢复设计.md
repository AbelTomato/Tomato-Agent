# 统一助手 Runtime 决策协议与长期恢复设计（计划日期：2026-10-12）

> **文档状态**：架构设计稿。2026-10-12 已冻结本期决策/事件协议语义；协议 Schema、助手决策解析/状态分流及阶段消息事件追加持久化已完成。工具状态事件、Provider 原生结构化输出与真实 Provider 兼容验收仍待后续。实施进度与具体落地范围以[实施计划](/home/abeltomato/workspace/projects/Tomato-Agent/docs/实施计划/2026.10.12-统一助手Runtime决策与事件协议实施计划.md)为准。本文其余未决问题仍需后续讨论，不表示相应运行时行为均已实现。

## 1. 背景与目标

统一助手首期真实验收发现：模型以普通最终文本请求澄清或工作区绑定时，策略层仍会把 `kind=final` 直接转换为响应，Run 因而进入 `completed`，却没有持久化等待动作。问题不是工作区授权被绕过，而是模型表达与 Runtime 状态转换之间缺少稳定协议。

本设计讨论目标是将 Agent Runtime 建模为一个由服务端控制、可持久化恢复的状态机：模型每轮提交明确的结构化决策，服务端校验协议、执行状态、权限及能力前置条件后，才推进 Run。目标支持渐进式能力发现和长时间人工等待后的恢复，同时保留单次执行与累计资源预算。

当前项目已经具备 SQLite 执行快照、事件与操作账本、Attempt/租约/fencing、版本化动作、等待后恢复原 Run、共享模型调用预算及完成结果校验。本设计应扩展这些边界，不另建与现有账本竞争的事实来源。

### 2.1 单次 Run 的消息与完成语义

- `message` 只向用户发送内容，不结束 Run；发送后 Runtime 仍可继续决策、查询能力或调用工具。
- `finish` 是唯一的单次 Run 结束语义。模型只能提交完成提议；只有服务端完成门禁通过并持久化终态后，Run 才能进入 `completed`。
- `finish` 的完成门禁只负责验证 Runtime 协议与执行闭环，不评价任务效果或答案语义质量；闭环成立且无未决动作/操作、未知副作用后即可完成。
- `finish` 结束单次 Run，不关闭 Session。Session 可继续接收新请求并创建新的 Run；新请求不得复活或回写已结束 Run。
- 普通文本、无法解析的响应和协议违规响应均不得隐式转换为 `finish`。

### 2.2 结构化决策与校验

- Runtime 决策采用固定版本化 JSON 对象；每次模型响应只包含一种决策类型，并由相应严格 Schema 校验。
- Provider 的 HTTP 响应外壳是 JSON，不代表其中的模型内容已是可信结构化决策。Provider 适配器需提取模型决策并解析；Runtime 统一按应用协议校验。
- 优先使用 Provider 原生 JSON/JSON Schema 结构化输出能力。原生能力不可用时，可采用兼容输出并严格解析；不能把兼容模式理解为放宽执行校验。
- 不支持原生结构化输出的 Provider 默认拒绝接入 Runtime。只有指定的 Provider/模型版本通过协议验收后，才允许受控兼容模式：提示输出 JSON、语法修复、严格校验及同一模型有限纠错。验收资格绑定到明确的 Provider 与模型版本，不因同 Provider 的其他模型通过而自动继承。
- 不使用第二个模型专门重写主模型输出，避免额外延迟、成本和语义改写风险。
- 语法修复仅用于格式层。修复后的对象仍必须完整通过 Schema 与状态校验；需保留原始响应、修复结果及校验结果，不能把推断出的业务语义当作原始决策。
- 对可纠正的模型决策错误，原模型最多额外调用一次进行纠错；该次数计入同一 Run 的调用和费用预算，跨恢复不重置。此上限不适用于 Provider/网络重试策略，后者需单独定义且不得产生重复决策提交。
- 纠错候选错误分为：响应解析/Schema 错误；决策与当前 Runtime 状态不匹配；服务端权限/安全拒绝；Provider/执行基础设施故障。前两类可考虑向原模型反馈一次；权限/安全拒绝及基础设施故障不能通过让模型改写决策解决。细分触发条件仍待确认。
- 不将未经筛选的 Pydantic 异常或含敏感数据的内部状态原样回送模型。纠错反馈使用字段路径与规则说明。

### 2.3 人工输入与授权边界

- `ask_user` 表示需要用户输入或选择，并由服务端创建持久化待处理动作。用户回答后恢复同一个 Run。
- 候选项和自由输入配置属于交互数据。模型可以提供问题和候选项，但动作 ID、版本、允许的响应形式由服务端生成。
- 模型建议或用户选择均不自动授予工具权限。工作区绑定、工具审批等授权事实只能由服务端按注册能力、用户动作和策略校验产生。
- 工作区缺失等可由服务端确定的前置条件，应在工具调用边界生成等待，而不是依赖模型在文本中声明绑定需求。
- 拒绝、取消、权限不足、超时和执行结果未知必须区分；拒绝不能被解释为授权或工具可重试失败。
- 普通消息与审批响应必须由不同的显式动作/接口识别；不得把任意文本推断为批准或拒绝。
- 等待中的 Run 存续期间，普通消息保留在同一 Session 并排队；当前等待 Run 恢复或结束后再消费。排队消息本身不修改 pending action，也不隐式恢复、取消或 steer 当前 Run。
- 仅当 Runtime 明确支持追加输入时，才允许将消息追加到暂停状态；追加内容必须作为输入经过该 Runtime 的校验流程，不能绕过 pending action、权限或状态门禁。
- UI/API 必须清楚区分“批准/拒绝”“回答当前 interrupt”“排队后续消息”“中断并 steer 当前 Run”四种意图。Steer 必须通过明确动作表达并遵循独立的状态/副作用安全校验；普通消息不能隐式 steer。
- Run 执行期间不接受会改变当前 Run 输入的新信息；用户只能提交独立、明确的中断动作。中断不等同于回答 interrupt/审批，也不隐式携带 steer 内容。

## 3. Runtime 决策类型建议

**本期已冻结（2026-10-12）**：首版采用下表六类决策，单个响应只能表达一种；字段级 Schema 与已完成事项见实施计划任务 1。`message` 可连续出现，受既有 Run 预算/无进展保护约束；`ask_user` 可提供候选项并允许自由文本，回答恢复原 Run，但不表示批准、拒绝、取消、steer 或工具授权。后端事件为追加式、版本化记录，含 Run/Step/调用关联身份、发生时间、摘要和类型化详情；不在本期提供 SSE/WebSocket、游标 API 或前端展示。旧客户端可忽略新增事件，现有 Run 查询响应保持兼容。

以下是讨论中的协议方向，最终字段及 Schema 仍待确认。

| 决策类型 | 语义 | 服务端处理方向 |
|---|---|---|
| `message` | 阶段性用户可见消息 | 记录事件并展示，Run 不结束 |
| `ask_user` | 请求澄清、选择或补充信息 | 创建版本化待处理动作，Run 进入 waiting |
| `discover_tools` | 按类别或关键词发现能力 | 从服务端注册目录返回能力摘要 |
| `describe_tool` | 请求特定能力的调用契约 | 返回参数 Schema、约束、可用性和契约版本 |
| `call_tool` | 请求调用已发现能力 | 服务端重新校验名称、版本、参数、权限和前置条件后执行或等待 |
| `finish` | 提交本次 Run 结果 | 通过完成门禁并持久化后结束 Run |

决策对象建议包含 `protocol_version`、唯一 `type` 和类型专属 `payload`。模型提供的 `decision_id` 可用于关联追踪，但不作为授权或幂等凭据；服务端负责生成事件 ID、动作 ID、版本和调用身份。

`message`、`ask_user`、`finish` 必须是不同的控制语义。结构化输出能避免裸文本自动结束 Run，但不能证明模型语义正确：模型仍可能将索取必要信息的内容错误提交为 `finish`。JSON Schema 不应被描述为语义正确性的保证。

## 4. 渐进式能力发现

### 4.1 目录与调用格式

- 初始模型上下文提供决策协议、当前 Run 状态、服务端能力分类及少量常用能力，不必一次发送全部工具参数 Schema。
- `discover_tools` 查询类别或关键词，服务端返回名称、用途、可用性、前置条件和审批要求。
- `describe_tool` 查询特定工具的完整契约，包括参数 Schema、约束与契约版本/摘要。
- `call_tool` 引用已查询契约版本；服务端始终使用当前注册表重新验证，不能信任模型自行构造的能力定义或过期参数。
- 若模型提交尚未加载的工具调用，Runtime 自动查询服务端目录并加载该工具契约；工具已注册且可用时继续按当前契约校验，不消耗模型决策纠错次数。工具不存在或不可用时返回明确服务端错误，不执行该调用。
- 若调用引用的工具契约版本已过期，Runtime 可执行已定义且语义保持的无损参数迁移；不能证明无损时不得猜测或执行，应将新契约和校验错误反馈模型，消耗唯一一次模型决策纠错机会。迁移规则和兼容版本范围必须由服务端定义。
- 工具已注册但当前不可用时按原因分流：可由用户补足的前置条件（如绑定工作区）由 Runtime 创建对应持久化等待；能力关闭或配置不可用时返回明确错误，可让模型使用唯一一次纠错机会改选能力或请求用户澄清；权限/安全拒绝直接停止该执行路径，不允许模型纠错绕过。
- Run 阶段是决策处理的硬门禁：`waiting` 只接受与当前 `pending_request` 匹配、且身份/版本/幂等校验通过的用户动作；等待期间不接受模型提交的新决策。终态 Run 拒绝所有新决策，不自动恢复或重路由。阶段冲突不消耗模型纠错机会。
- `finish` 通过协议/Schema 校验但被 Runtime 闭环门禁拒绝时，协议错误可按唯一一次纠错规则处理；仍有未决动作、未完成操作或未知副作用属于 Runtime/执行状态冲突，硬拒绝 `finish`，不允许模型通过改写结果绕过；按对应恢复或失败路径处理。不因任务效果不足、缺少通用测试或语义质量判断拒绝 `finish`。
- Provider/网络故障不属于模型决策纠错：只有能确认请求未被 Provider 接收时，才允许对同一模型调用自动重试一次；超时、连接中断或响应丢失等结果不确定情况，将模型调用记为未知并暂停 Run，进入核实/人工恢复，不得启动新决策覆盖未知调用。
- “可重试”不等于“可安全重放”。自动重试的证据限于传输层能证明请求未发送/未抵达服务端（如 HTTP 请求尚未启动、连接建立前失败且确认没有发送请求字节），或该 Provider/模型/网关版本的幂等重放语义已通过验收且同一逻辑调用复用同一个幂等键。仅仅发送 `Idempotency-Key`、收到 `Retry-After`/泛化 5xx、取得 Request ID 或客户端没有收到响应，均不单独构成安全重放证据。
- Provider 适配器应尽可能记录传输事实（请求是否启动、发送字节阶段、HTTP 响应/响应体是否开始、Provider Request ID、重放安全分类及证据来源）。不能确定是否抵达或处理时按 `UNCERTAIN` 处理，不依据异常名称猜测请求未被接收。
- 自动传输重试计入独立的基础设施/网络故障重试预算，不计为新的模型逻辑决策调用；但每次实际 HTTP 尝试必须单独审计，Provider 可能收费的事实仍需记录。模型决策调用预算按逻辑调用计量；经用户知情同意后为未知调用新发起的模型请求属于新的逻辑调用并消耗模型预算。
- 自动传输重试采用两层上限：每个逻辑模型调用最多自动重试 1 次；每个 Run 累计最多自动传输重试 2 次。两层限制必须同时满足，并受 Run 剩余执行时限约束。该预算只限制已有安全重放证据的自动重试次数，不扩大可安全重放的错误范围。
- 对无法通过 Provider 查询或安全重放恢复的未知模型调用，允许用户在 UI 明确知情同意后，于原 Run 内启动一个新的模型调用继续；不得将旧未知调用改记为失败或覆盖其记录。知情同意需明确提示旧调用可能仍在 Provider 侧执行/计费，新调用可能造成重复生成或费用。
- 未知调用恢复采用双轨审计：原调用作为不可变的 `UNCERTAIN` 轨迹保留；经用户确认后创建关联的新调用轨迹，记录同意主体/时间/提示版本、父未知调用 ID、输入摘要、Provider 响应及后续决策。新调用结果不得伪装成旧调用结果。
- 用户确认重试后，对原 Run 采用保守防御锁：锁住所有由服务端能力元数据标记为副作用的工具；已确认只读的工具仍可继续。锁保持到旧调用确认终止，或用户对冲突作出明确处理；只读/副作用分类必须由服务端能力定义，不由模型声明。未解锁前不得执行副作用工具。
- 未知调用若在新调用启动后迟到返回，必须按旧调用 ID 归档到原审计轨迹，不得覆盖新调用响应或自动执行其中的工具决策。Runtime 通知用户存在冲突并继续锁住副作用工具，要求用户明确选择：忽略旧响应并继续当前新调用轨迹、采用旧响应并基于它重新规划，或终止 Run。选择本身作为版本化、幂等且可审计的服务端动作；未选择前 Run 保持等待。
- 用户选择采用迟到旧响应时，不删除或覆盖新调用及其后续只读结果；将该新轨迹标为 `abandoned`，从旧响应对应检查点建立可审计的新决策分支，并重新验证上下文、能力契约与权限后再继续规划。若用户选择忽略旧响应，则旧响应只作审计事实，继续新调用轨迹；若终止，则 Run 进入终态，副作用锁保持为终态审计信息，不再执行工具。
- 工具目录仅说明能力事实，不赋予权限。未注册能力不可调用；已注册但不可用的能力须返回明确状态；需工作区或审批的能力由 Runtime 生成相应等待动作。
- 当前未接入的能力（例如 `apply_patch`）只能标示为不可用或未注册，目录协议不能伪装成能力实现。

### 4.2 延迟与缓存权衡

渐进加载能缩小常规上下文，但额外目录和契约查询会增加模型往返。建议小而常用的能力预加载，低频或参数复杂工具按需查询，并在 Run 内复用已查询的契约。不可把“每次调用工具前都查询两次”设为固定流程；应结合调用成本和能力规模决定加载策略。

## 5. 状态机建议

公开 Run 状态可继续使用 `queued`、`running`、`waiting`、`completed`、`failed`、`cancelled`、`timed_out` 等有限状态；内部阶段需更细，区分准备决策、决策已接收、工具待执行、工具执行中、结果已记录、等待恢复和完成校验。

| 当前阶段 | 输入/决策 | 服务端动作 | 结果阶段 |
|---|---|---|---|
| `ready_decision` | `message` | 保存可见消息和决策事件 | `ready_decision` |
| `ready_decision` | `ask_user` | 原子保存待处理动作及快照，释放执行租约 | `waiting` |
| `waiting` | 合法用户回应 | 校验 Session、动作 ID、版本、幂等键并原子消费 | `ready_decision` |
| `ready_decision` | `discover_tools` / `describe_tool` | 服务端查询目录并持久化决策结果 | `ready_decision` |
| `ready_decision` | `call_tool` | 校验能力、契约、权限、参数和前置条件 | `tool_ready` 或 `waiting` |
| `tool_ready` | 工具结果确定 | 保存操作结果、证据和产物引用 | `ready_decision` |
| 工具执行阶段 | 结果未知或旧执行所有者失效 | 禁止盲目重放副作用，进入核实/恢复等待 | `waiting` |
| `ready_decision` | `finish` | 校验协议有效、执行闭环完成且没有未决动作/操作或未知副作用 | 通过后终态 `completed` |

公开状态可统一为 `waiting`，再以结构化 `pending_request.kind` 区分用户澄清、工作区绑定、工具审批、未知副作用核实或预算续期，避免为每种等待原因增加不必要的顶层状态。

## 6. 完成门禁

`finish` 是模型提交的候选结果，不是完成事实。服务端门禁只验证 Runtime 协议与执行闭环，不评价任务效果或答案语义质量；至少验证：

- Run、Session、快照版本、当前执行所有者和策略上下文一致。
- 不存在未消费的 `pending_request`。
- 不存在未完成或结果未知的操作。
- 最终结果符合该任务类型的严格 Schema 和响应预算。
- 若结果包含引用或声明服务端执行过的产物/测试/能力输出，则这些结构化声明必须与 Run 内已有事实一致；不要求所有任务提供通用证据或测试。
- 当前授权、工作区和能力策略仍有效。

校验失败不得标记 `completed`。可修复的协议问题可在剩余预算内反馈模型；权限失败、所有权失效、未闭合执行或未知副作用必须走对应失败/恢复路径。门禁不判断任务效果或开放式答案是否充分。

## 7. 持久化与长期恢复

### 7.1 Run 内执行 Step 与串行约束

- Run 是长期任务及跨步骤审计容器；恢复事件记录不可变触发事实，例如初始请求、用户对 pending action 的回应，或用户同意处理未知模型调用。
- 每个被接受的触发事件可原子创建一个持久化执行 Step。Step 是一段 `reasoning-acting` 工作单元，拥有局部失败重试预算、检查点、模型逻辑调用、传输尝试、工具操作、等待点和结束原因。恢复事件是输入事实，Step 是执行与预算归属单位，两者不可混为一个记录。
- 首期同一 Run 内 Step 串行，任一时刻最多一个活动 Step。并发恢复提交通过唯一且不复用的动作 ID 与持久化事务/条件状态迁移竞争；至多一个请求能消费 pending action 并创建后继 Step，其余返回 `409 Conflict`，不得并行执行或重放首次 HTTP 响应。
- Step 进入人工等待时释放 Worker/租约并挂起；用户合法回应被持久化消费后，创建后继 Step。等待不是失败，也不消耗 Step 的失败重试次数。
- 前序 Step、模型调用和工具操作的审计记录不因创建后继 Step 而清零。未知调用的用户同意恢复会创建关联的新 Step；旧未知调用及 Run 级副作用防御锁跨 Step 保留。
- Step 局部预算如何与 Run 级累计资源硬上限组合尚未决定；新 Step 不应隐式删除历史消耗或未知副作用状态。

### 7.2 等待与恢复

- 人工等待期间不持有 Worker、进程内 Promise 或执行租约。Run、待处理动作、回应和当前检查点均写入持久化存储。
- Run 和 pending action 永不过期；等待时长本身不终止 Run、不消耗执行 Step 的失败重试预算。该决定不免除用户主动取消、管理员治理或底层数据保留政策的另行处理。
- 用户回应通过服务端动作接口提交，并检查身份、Session/Run 归属、唯一且不复用的动作 ID、允许动作及冻结参数；动作 ID 不设置单独版本号。
- interrupt/pending action 只能被原子消费一次：首个有效提交消费动作并触发同一 Run 恢复；动作已消费、已失效或不存在时，重复/迟到提交直接返回 `409 Conflict`，不重放第一次提交的 HTTP 响应，不创建重复恢复事件或 Step。该幂等性只保证服务端状态与副作用不重复，不承诺重复请求返回原结果。
- 并发提交时，由持久化事务/条件状态迁移决定唯一胜者；其余请求返回 `409 Conflict`。恢复后 Run 可能仍在调度或执行，interrupt 提交接口的响应不是 Run 结果；客户端应通过独立的 Run 状态/结果接口查询进度。
- 用户合法动作被接受后，恢复同一 Run 并创建串行后继 Step；用户回复不是失败，也不重置已有 Step 的计数。后继 Step 的局部执行预算重新开始，但 Run/操作/调用历史保留。
- Worker 恢复时从最后一个已提交检查点继续；不重复已提交的消息、已完成操作或已消费动作。
- 事件历史用于审计与恢复诊断，版本化快照用于快速恢复。两者应使用明确的协议和 Schema 版本；未知版本不得按猜测解释。
- 普通 waiting 恢复继承 Run 已绑定的授权和环境状态，不因等待本身要求重新授权。恢复仍须校验动作身份、Run 所有权和快照完整性；若环境/授权实际被撤销或不再可用，按服务端拒绝/恢复流程处理，不把历史授权扩展为新的权限。

### 7.3 用户取消与不可控操作脱离

- 用户取消是终止当前 Run 的停止请求，不是可恢复的 `interrupt/approval`，也不承诺撤销已发生的外部副作用。
- Run 原子进入 `canceling` 后立即锁定控制面：禁止调度新的模型轮次和工具步骤，并尽力向当前模型请求、支持取消的异步工具及子任务传播取消信号。
- Runtime 收拢可取消任务并清理资源。对不响应取消或无法安全终止的工具调用，持久化标记为 `detached/orphan`，解除 Run 对其返回结果的强等待依赖；Run 可在取消收尾后进入终态 `cancelled`，不必等待孤儿操作返回。
- 孤儿操作后续成功/失败/超时只更新独立操作账本与审计事件；不得回写已取消 Run 的结果或对话历史，不得触发后续模型/工具步骤，也不得污染其他 Run。
- 所有外部工具调用必须有硬超时。可能产生副作用的工具应使用幂等键，并在能力可用时提供状态查询/对账或补偿接口；幂等只防止重复，不代表回滚。Runtime 不因取消自动假定副作用已撤销，也不自动承诺补偿成功。
- Run 的 `cancelled` 终态与孤儿操作的最终状态分离：Run 可终结，操作审计仍可异步补充；任何补充不得改变 Run 终态。

### 7.4 时间与预算分离

“Run 可长期恢复”指等待时长不强制让 Run 失效，不代表执行和费用没有上限。推荐区分：

- Run 存续/保留策略：与单次执行超时分开；具体最长保留期限尚未决定。
- 人工等待：不占 Worker、不持有租约、不消耗执行时长。
- 单次模型/工具调用：仍有调用超时和取消。
- 单次 Worker 执行片段：有时限，达到上限后保存检查点并让出调度。
- Run 累计模型调用、工具调用、Token/费用预算：持久化累计，恢复不清零。
- 累计预算耗尽：进入明确的预算等待/终止路径；新 Attempt 不自动获得额外预算。

### 7.5 预算默认值（设计基线）

- 单个执行 Step 的失败重试预算：最多自动重试 3 次（即首次执行之外最多 3 次重试）；同一 Step 的 retry/continue 恢复共用计数。人工 waiting、用户回复和正常工具结果不增加失败计数；进入后继 Step 不会改写前序 Step 的计数。
- 单个 Step 的资源上限暂沿用当前助手默认值：最多 12 次模型逻辑调用、8 次工具调用、120 秒活动执行时间；单次模型请求 60 秒、单次工具调用 20 秒，均受 Step 剩余时间限制。以上是设计默认值，实施时仍需确认配置可覆盖与持久化快照记录。
- 自动传输重试仍独立于模型逻辑调用：每逻辑调用最多 1 次、每 Run 累计最多 2 次，并受活动 Step 的执行时限约束；只对具备安全重放证据的请求适用。
- 基础设施重试预算耗尽后，不自动重试；若调用结果不确定，按 `UNCERTAIN` 和显式知情恢复流程处理。
- 暂不设虚构的货币费用上限；是否需要 Run 级费用/token 硬上限及具体值，需结合 Provider 价格、产品额度和实际 usage 计量能力另行确定。新 Step 有局部上限不代表 Run 累计资源无限制可以不治理。

### 7.6 副作用与恢复

每次工具调用在发起前生成稳定、唯一的 `invocation_id`，并持久化调用身份、工具/契约标识、参数摘要、启动时间、尝试信息及可得结果引用；记录状态至少区分 `pending`、`running`、`succeeded`、`failed`、`unknown`。工具调用及状态变化应有可关联的 Observe/trace/audit 记录。Runtime 的 trace 只能证明本地调度/观测到的调用事实，不得冒充外部副作用已发生或未发生的证据。

- 超时、进程崩溃或响应丢失只说明当前执行方未确认结果；不得据此将副作用调用直接判为失败或自动重放。先将调用标为 `unknown` 并保留原记录。
- 工具结果按以下互斥类别处理：`not_started`（有传输/调度证据证明外部执行未开始）、`succeeded`（收到并持久化成功结果或权威查询确认成功）、`failed`（工具明确返回失败，且其契约说明该失败状态及副作用边界）、`unknown`（超时、崩溃、连接中断、响应未持久化，或证据不足以归入其他类别）。分类必须记录证据来源；仅凭异常类型或缺少响应不得推断 `not_started`/`failed`。
- `not_started` 可在 Step 重试预算内重试；`failed` 按工具契约和错误类别决定是否可重试，副作用状态不明时必须归 `unknown`；`succeeded` 不重放；`unknown` 遵循本节的权威查询、同键幂等恢复或人工 interrupt 路径，不消耗普通失败重试来掩盖不确定性。
- 优先通过工具服务提供的权威状态查询接口，按 `invocation_id` 或工具契约定义的关联标识核实结果；只有查询证据满足契约定义的判定条件时，才可自动转为成功/未执行等确定状态。
- 服务端不支持查询但支持并保证同一幂等键重放时，可依据该工具契约使用原 `invocation_id`/幂等键恢复；不得换新键重发同一逻辑操作。
- 对非幂等副作用且无可靠查询接口的工具，`unknown` 必须进入持久化人工 `interrupt`，不得自动重试或继续可能冲突的副作用步骤。通过明确 UI/API 动作要求用户核查外部当前状态；核查完成前隔离同一冲突域内会造成重复或矛盾副作用的操作。Runtime 无法从本地 trace 推断外部真实状态。
- 人工核查动作明确提供“确认已执行”“确认未执行”“仍无法确认”三种结果，作为独立恢复事件持久化并关联原 `invocation_id`，不得改写原始未知调用事实。“确认已执行”可据此结算原操作并继续；“确认未执行”仅在工具契约允许安全重试时才可用原调用身份/幂等键重试，否则保持隔离并要求进一步处置；“仍无法确认”保持 interrupt、隔离冲突域副作用且不重放。若用户无法核实，则可保持等待或明确终止/处置，不自动猜测。
- checkpoint、对话历史和 Observe/trace 能帮助重建执行上下文，但不能单独确认外部副作用。对账/补偿仅在工具契约明确支持时执行；幂等键防重复，不等同于撤销已发生操作。

## 8. 决策解析、纠错与 Provider 能力

建议按以下顺序取得可校验决策：

1. Provider 支持时使用原生结构化输出/JSON Schema。
2. 提取模型决策内容，做必要的 JSON 语法解析；若采用 `json-repair` 等语法修复库，修复不得绕过必需字段、枚举、额外字段禁止、业务规则和状态转换校验。
3. 对修复后的对象执行严格 Schema 校验。
4. 校验失败时，将筛选后的字段路径和期望格式反馈给同一模型，要求纠正；重试消耗原 Run 预算。
5. 超出上限、响应不可解析或 Provider 能力不满足协议时，以明确错误/不可用状态结束本次执行，不把文本猜成默认决策。

具体修复库、是否要求 Provider 原生结构化输出、兼容模式允许范围及纠错次数尚未决定。语法修复结果必须可观测，不能静默改写业务意图；不增加第二个模型充当格式转换器。

## 10. 未决设计问题与讨论顺序

以下问题尚未拍板，应逐项讨论，不在实施时自行假定：

1. **协议输出与 Provider 兼容**：已确认不支持原生结构化输出时默认拒绝；Provider 兼容验收暂缓设置，当前不确定验收用例、通过标准、模型版本资格失效规则及语法修复库选择。此前提出的“100% 通过”仅为临时讨论意见，尚未采纳为门槛。
2. **协议纠错适用错误类型**：已确认可纠正的模型决策错误最多额外调用原模型一次。解析/Schema 错误、不可用能力（配置关闭或不可用）及可修正的完成结果内容错误可触发纠错；未发现工具由 Runtime 自动查目录/加载契约，不耗纠错；过期契约先尝试服务端定义的语义保持无损迁移，否则反馈新契约并耗一次纠错。可由用户补足的前置条件转等待。权限/安全拒绝、Run 阶段冲突、未决操作/未知副作用及 Provider/执行基础设施故障不得由模型纠错绕过。Provider 自动传输重试最多一次，只有传输层证明请求未发送/未抵达，或指定 Provider/模型/网关的同 Key 幂等重放能力已验收时才允许；否则进入 `UNCERTAIN`。`Retry-After`、泛化 5xx、Request ID 或无响应本身不是安全重放证据。用户明确知情同意后可在原 Run 创建新调用，旧调用保留为不可变未知记录并与新调用双轨关联；该恢复不是模型纠错。确认锁住原 Run 的所有副作用工具、允许只读工具继续；锁至旧调用确认终止或用户明确处理冲突。迟到响应归档并通知用户，用户需选择忽略旧响应继续、采用旧响应重规划或终止 Run；选择前保持等待和副作用锁。采用旧响应时保留并标记新轨迹 `abandoned`，从旧响应检查点建立新分支，重验上下文与权限。仍需确认解析错误细分及其他门禁错误分类。
3. **决策类型的完整边界**：`message` 是否允许连续出现，何时需要避免无进展循环；`ask_user` 选项结构、自由输入以及用户新增文本的交互定义。
4. **工具目录策略**：未发现工具时 Runtime 自动查询并加载契约已确认；过期契约只允许服务端定义的语义保持无损迁移，否则要求模型按新契约重决策；工具不可用按前置条件等待、配置错误纠错、权限拒绝停止分流。初始预加载范围、分类与搜索接口、迁移兼容版本范围和 Provider 工具调用格式仍待讨论。
5. **用户消息与 Run 生命周期**：已确认普通消息与审批响应分离；等待中的 Run 存续期间，普通消息在同一 Session 排队，当前 Run 恢复或结束后再消费。只有 Runtime 明确支持并经过输入校验时才追加到暂停状态；UI/API 区分批准/拒绝、回答 interrupt、排队后续消息和中断并 steer。Run 执行期间只接受明确中断动作，不接受改变当前 Run 输入的新信息。具体接口形状及 steer 的安全校验细节仍需在协议/API 设计阶段定义。
6. **等待动作生命周期**：已确认 Run/pending action 永不过期；pending action 使用唯一且不复用的 ID，不设单独版本号。首次有效提交原子消费并触发恢复，重复/迟到或并发失败提交均返回 `409 Conflict`，不重放首次 HTTP 响应。无独立撤回动作；切换会话不使原 Session 的 pending action 失效，其余会话切换体验细节可在 UI/API 设计时处理。
7. **完成门禁**：已确认 `finish` 只要求 Runtime 协议合法、执行闭环完整且无未决动作/操作或未知副作用；不评判任务效果/答案质量，也不强制通用证据或测试。具体结果 Schema 和与 Run 内事实一致性校验规则由实现按任务类型定义。
8. **长时恢复兼容**：已确认普通等待恢复继承授权和环境状态；仍需讨论快照/决策协议迁移、工具契约变化、Prompt/策略变化、部署升级及实际权限撤销/环境改变时的继续/迁移/重新确认策略。
9. **预算模型**：已给出设计默认值：Step 失败后最多自动重试 3 次；每 Step 最多 12 次模型逻辑调用、8 次工具调用、120 秒活动执行时间，单模型请求 60 秒、单工具调用 20 秒；传输重试每逻辑调用最多 1 次、每 Run 总计最多 2 次。等待不计失败，用户合法动作触发后继 Step，旧 Step 计数和审计不重置。仍需讨论是否设置 Run 累计费用/token硬上限、具体额度和预算耗尽后的续期身份/批准方式。
10. **Run 保留与数据治理**：已确认 Run 和 pending action 不因时间自动过期；仍需讨论审计数据、消息、工具输入和证据的保留/归档/删除政策，以及用户取消和管理员治理。
11. **副作用恢复等级**：已确认每次调用使用稳定 `invocation_id` 并持久化 Observe/trace/audit；未知结果优先走权威查询，其次仅按工具契约使用同一幂等键恢复。非幂等副作用且无可靠查询接口时进入人工 interrupt，核查选项为“确认已执行/确认未执行/仍无法确认”；未确认前隔离冲突域并禁止自动重放，确认未执行时仅按工具契约安全重试。仍需定义能力分类细节，以及取消中孤儿操作的长期跟踪、对账和补偿。
12. **分阶段迁移与兼容**：现有 Assistant v1 快照、旧 Provider 响应、前端消息和 Run API 的版本协商、读兼容与停止写旧协议的时点。
