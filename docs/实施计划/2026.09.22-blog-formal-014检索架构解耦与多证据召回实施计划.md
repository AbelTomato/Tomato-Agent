# blog-formal-014 检索架构解耦与多证据召回实施计划（计划日期：2026-09-22）

> **执行说明：** 按任务顺序逐个实现；每个任务先补失败测试，再做最小实现和目标验证。本文只描述实施方案，不代表功能已经完成；真实博客 `test` 集在 `dev` 验收通过前不得查看、调参或调用外部模型。

**目标：** 修复跨文章、多证据问题的检索假阴性，在不牺牲无答案拒答能力的前提下，使 `blog-formal-014` 的两组正文证据能够进入候选池、完成最终证据选择并被引用回答。

**架构：** 将当前 `KnowledgeService` 中耦合的“召回、排序、证据选择、是否回答”拆成稳定的流水线：`QueryPlanner → CandidateRetriever → Ranker → EvidenceSelector → AnswerabilityJudge → Answerer/CitationValidator`。候选召回只负责尽量不漏，Rerank 只负责相关性排序，证据选择负责多证据和来源覆盖，`AnswerabilityJudge` 才负责 `supported / insufficient / no_results`；任何一个阶段不得用自己的分数替代其他阶段的职责。

**技术栈：** Python >=3.11、现有 FastAPI、Pydantic、aiosqlite、httpx、tiktoken、pytest、pytest-asyncio；不新增未确认的第三方依赖。Rerank 通过内部 `Reranker` Protocol 隔离具体外部服务，离线测试使用 Fake Provider。

**设计依据：**

- `docs/development-log/2026-09-22.md`：v3 front matter 污染已修复，v4 仍存在 `blog-formal-014` 在 `0.5` 门槛下空结果、降低门槛后无答案题误召回的问题。

- `docs/评测/评测规范.md`：保留集隔离、单片段证据覆盖口径、无答案与执行失败分开统计。

- 现有 `KnowledgeService.retrieve()`、`answer()`、`KnowledgeAnswer`、`CitationSnapshot` 和 API 响应字段保持向后兼容；新增字段必须可选或有默认值。

## 现状问题与目标行为

### 已确认的现状

`blog-formal-014` 的问题是“Q/K/V 职责”和“多头注意力独立子空间”两个证据面的跨文章组合题。v4 中 YAML front matter 已排除，但默认 `min_vector_similarity=0.5` 下没有候选；诊断模式在 `0.0 + top_k=20` 时才找到两条正文证据，排名分别为第 1 和第 7。单纯降低门槛会让 3 个无答案题全部出现非空召回。

当前主要耦合为：

```text
KnowledgeService.retrieve()
  → Repository vector/hybrid search(limit=5, min_score=0.5)
  → 空结果即 no_results
  → 非空结果直接作为最终证据
  → KnowledgeService.answer() 调用 LLM
```

目标行为为：

```text
原问题
  → QueryPlanner（保留原问题，必要时生成子查询）
  → CandidateRetriever（candidate_limit=30，宽松召回）
  → Ranker（RRF/向量初排 + 可选 Rerank）
  → EvidenceSelector（子查询覆盖、来源覆盖、去重、final_limit）
  → AnswerabilityJudge（supported / insufficient / no_results）
  → Answerer（仅对允许回答的证据调用 LLM）
  → CitationValidator（当前检索批次白名单）
```

明确禁止以下等价替换：

- 不得把 `candidate_limit=30` 直接改名为 `limit=30` 并把 30 条全部发送给 LLM。
- 不得把“候选非空”直接标记为 `supported`。
- 不得把 Rerank 失败转成空候选。
- 不得把 Rerank 分数直接复用旧 cosine `0.5` 阈值。
- 不得在未完成 dev 消融和无答案题复验前把新策略切为默认生产路径。

## 评测指标与判定规则

### 必须报告的指标

| 指标 | 定义 |
|---|---|
| Candidate Evidence Recall@30 | 标注证据是否出现在宽候选池，衡量召回阶段漏召回。 |
| Final Evidence Recall@5 | 标注证据是否进入最终交给 Answerer 的证据，衡量选择阶段损失。 |
| Multi-evidence coverage | 多证据题被覆盖的 query/facet 数除以所需数量。 |
| Source coverage | 最终证据覆盖的文档数与标注所需文档数。 |
| Answerable empty rate | 可回答题最终没有候选或没有可选证据的比例。 |
| Unanswerable nonempty rate | 无答案题候选池/最终证据非空的比例，分别统计。 |
| Supported rate | LLM 回答被人工或规则确认有足够证据支持的比例。 |
| Citation completeness | 答案是否引用所有必要证据面，至少单列 014。 |
| 阶段延迟 | QueryPlanner、召回、Rerank、选择、Judge、LLM 分别记录 p50/p95/max。 |
| Provider error rate | Embedding、Rerank、LLM 的执行失败单独计数。 |

### 不得使用的判定方式

- 不以候选池非空作为正确回答。
- 不以单个 top-1 cosine 或 Rerank 分数跨题直接比较。
- 不以空结果作为真实拒答质量的唯一证明。
- 不把 LLM 未调用的可回答 `no_results` 计入正确拒答。
- 不把执行错误计入空结果、正确拒答或 `supported`。

### 014 专项验收表

每个候选策略都必须填充以下表格，不允许只报告总体指标：

| 检查项 | 结果要求 |
|---|---|
| 原问题是否保留 | 必须是 |
| 子查询数量 | 1–4，记录具体文本和 facet |
| 两条标注证据是否进 candidate | 两条均是 |
| 两条标注证据是否进 final | 两条均是 |
| 两个文档是否覆盖 | 两个均是 |
| Judge 状态 | `supported` |
| LLM 是否调用 | 是；若否，记录原因并判该策略未通过 |
| 引用是否来自白名单 | 全部是 |
| 无答案题影响 | 不得从当前 `3/3` 正确拒答整体退化 |

## 风险、回滚与完成标准

### 风险与控制

| 风险 | 控制方式 |
|---|---|
| 候选扩大导致无答案题误召回 | 候选与 Judge 解耦；单独报告无答案 candidate/final 非空率；不以候选非空调用 LLM。 |
| Rerank 服务延迟、费用或不可用 | Protocol + Noop；超时和错误显式传播；离线 Fake Provider 与真实 Provider 分开报告。 |
| 查询分解生成错误事实 | 只允许输出子查询文本和 facet；保留原问题；解析失败安全回退；不接受模型提供 citation 或文档 ID。 |
| 多样性规则损害单文档问题 | 覆盖选择以 query/facet 为主，不强制每篇文档一个 chunk；保留简单问题回归测试。 |
| 分块边界导致证据未被单 chunk 覆盖 | 本阶段不改变标注口径和物理行号；若要引入相邻片段窗口，另增指标版本并单独实验。 |
| baseline 与新策略代码分叉 | 所有策略共享 `KnowledgePipeline` 阶段接口；Noop Reranker 和单 query planner 作为 baseline 实现。 |
| 外部实验污染保留集或业务库 | 只使用 v4 隔离数据库和 `dev`，输出目录不可覆盖，真实实验不写业务数据库。 |

### 回滚方式

1. 将 `knowledge_pipeline_enabled` 和 `knowledge_rerank_enabled` 恢复为 `false`，恢复旧 baseline 编排。
2. 保留已生成的候选/选择/判定报告，不删除临时工件，避免丢失失败证据。
3. 若服务接口出现兼容问题，只回滚 Service 注入和配置默认值，不回滚已验证的独立契约测试文件。
4. 若外部 Provider 持续失败，切换 Noop Reranker 进行离线召回/选择实验，不将结果标作真实 Rerank 收益。
