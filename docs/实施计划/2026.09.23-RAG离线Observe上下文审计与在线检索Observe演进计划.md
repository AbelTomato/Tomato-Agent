## 一、目标范围与阶段门禁

### 本期：离线 `dev` 上下文审计

本期产物必须让审阅者能从每个问题的原始检索候选，追至排序/筛选、Answerability 判定、最终模型上下文、LLM 返回、引用校验和人工语义支撑复核。`evaluation.py` 已存在候选/最终结果、Judge、阶段延迟、LLM 是否调用和引用完整性字段；实现时先复用并补足这些逐题数据，不平行创建另一套质量指标。

本期包括：

1. 版本化 Trace/Event 契约、结构校验、稳定序列化、事件关联和工件完整性校验。
2. pipeline 阶段轨迹：查询计划、候选检索、重排、最终证据选择、Answerability Judge；对每项候选记录其来源、排名/分数、证据身份和是否进入下一阶段。
3. Answerer 实际上下文审计：记录每次 `LLMClient.complete(messages, tools)` 调用在接口边界收到的完整参数及哈希，覆盖 query planner 与答案生成；记录 prompt 模板标识/版本/哈希、调用用途、耗时、成功/失败和适配器可见的重试/尝试信息。
4. 按问题保存答案、引用白名单校验结果、`supported`/`insufficient` 等机器判定，以及独立的人工语义支撑复核字段。
5. 本地报告目录中的逐题 Trace、汇总/provenance/校验清单和受控的完整输入；run 目录不可覆盖，运行不完整时保留失败状态和已生成的部分审计信息。
6. 单元、集成测试及显式批准后的隔离 `dev` 复验。

本期不包括：在线请求内容落盘、在线日志接入外部平台、生产 Observe UI/查询服务、RAG 检索策略优化、Benchmark 任务 1、创建 candidate、`test` split 的读取或评估。`blog-formal-014` 等既有准入问题仍依照评测规范跟踪；Observe 报告不能替代其解决，也不改变 Benchmark 启动门槛。

在线阶段须另立实施与审批切片，至少明确：显式功能开关及默认关闭、允许记录的字段白名单、提示词/证据正文的默认禁存策略、查询级脱敏、采样率与采样稳定性、访问控制/审计、数据留存期限、线上存储隔离、写入失败不得影响回答的隔离策略、成本/容量上限、告警、关闭和回滚验证。在线阶段未独立审批前，不添加在线 sink，不改变 API 行为，不持久化在线请求的 query、上下文、消息或答案。

## 二、Trace 契约与事件口径

### 2.1 Trace run 与事件字段

建议契约名为 `rag-observe-trace/v1`，用 Pydantic 严格校验；未来字段语义不兼容时递增版本，不静默重解释旧字段。每个 run manifest 至少包含：

| 字段 | 含义 |
|---|---|
| `trace_schema` | 固定为 `rag-observe-trace/v1`。 |
| `run_id` | 每次运行唯一 UUID；路径冲突必须失败，不覆盖旧目录。 |
| `environment` / `split` | 固定 `dev`；任何非 `dev` 值由 runner 拒绝。 |
| `started_at` / `finished_at` | UTC RFC 3339 时间；未完成时 `finished_at=null`。 |
| `status` | `running`、`complete` 或 `incomplete`；存在任何逐题执行错误时不得标 `complete`。 |
| `dataset` / `snapshot` | 数据集与隔离知识快照的路径标识、SHA-256、版本/文档清单指纹；禁止记录业务数据库数据。 |
| `implementation` / `configuration` | 源码 revision 或相关文件指纹，以及允许列表中的检索/模型/提示词/限额配置；不记录密钥、Token、完整环境变量或 Authorization Header。 |
| `artifacts` | 每个相对文件路径、字节数和 SHA-256；manifest 自身不纳入自身哈希。 |

每条 Event 至少包含 `schema_version`、`run_id`、`question_id`、单调递增 `sequence`、UTC `occurred_at`、`event_type`、`status`、`duration_ms|null`、`payload`、`previous_event_sha256` 和本事件 `event_sha256`。哈希使用 UTF-8、固定字段排序和无额外空白的 canonical JSON；当前事件哈希覆盖除自身哈希字段外的规范化事件内容。事件链断裂、重复序号、未知版本、负延迟或摘要不匹配必须使完整性校验失败。

### 2.2 阶段事件

每个问题至少按实际发生顺序发出以下事件；未执行阶段显式记 `skipped` 及原因，不伪造空成功结果：

1. `question.started`：问题 ID、split、输入查询指纹；完整用户 query 只在本地受控逐题工件保存。
2. `query_plan.completed`：原始检索查询与计划子查询、query ID、规划策略、prompt 指纹及耗时。
3. `retrieval.completed`：每个子查询的候选结果、chunk/document/version/source 行区间、检索排名、score 类型/值、关联 query ID；合并去重后的候选仍须可追溯到各子查询。
4. `rerank.completed`：重排前后次序及分数；未启用重排须标注 `noop/disabled`，不可将原始分数误标成 rerank 分数。
5. `evidence_selection.completed`：候选逐项记录 `selected`、最终次序及排除原因；当前 selector 的排除原因至少区分 `final_limit` 和 `duplicate_chunk`。若未来策略无法给出更细解释，使用 `not_selected_by_selector`，不得推断算法内部原因。
6. `answerability.completed`：证据状态、Judge reason、覆盖率/confidence、Judge 配置指纹；此字段只是机器判定，不是答案正确或语义支撑结论。
7. `llm.request` 与 `llm.response`：调用用途、attempt 编号、模型标识、准确的接口入参/响应结果、耗时、成功/失败。未调用 LLM 时明确记录跳过原因。
8. `citation_validation.completed`：模型给出的 citation IDs、请求标签到真实 citation/chunk 的映射、引用是否属于白名单及映射回的快照身份；仅记录自动可验证事实。
9. `answer.completed` 或 `question.failed`：最终 answer、`evidence_status`、整体执行状态、可分离的阶段耗时和错误分类。错误记录异常类型/稳定错误码，不直接落完整异常文本、请求头或环境配置。

对候选证据、Answerer 最终上下文、模型输出引用和人工认为语义支撑的证据分别使用不同字段/实体，不用 `supported` 替代答案正确性。每题单独的人工复核记录至少区分 `correctness`、`completeness`、`groundedness`、`citation_fidelity`，每项使用 `pass`/`partial`/`fail`/`not_reviewed`，并记录复核时间、非敏感 reviewer 标识、依据的 citation/chunk ID 和简短理由；尚未复核时必须是 `not_reviewed`，不得自动赋值为通过。

### 2.3 精确 LLM 接口输入的定义

`llm.request.messages` 是调用 `LLMClient.complete(messages, tools)` 前，在客户端抽象接口处对实际 `messages` 和 `tools` 参数的顺序化、可逆序列化；同时记录 canonical JSON 的 SHA-256。序列化保留 `Message` 的 role/content/tool-call/tool-call-id 等字段，不重排或归一化内容。答案生成当前传入空 `tools` 列表时，工件也必须如实记录空列表。

这只证明程序传给 `LLMClient` 的参数，不证明 Provider 收到的原始 HTTP payload。适配器可能添加模型字段、转换 message 格式、加入 Header、编码请求或改变传输；本期不拦截、不保存原始 HTTP 请求/响应 Header。不得记录 API key、Authorization Header、环境变量、签名或其他凭据。Prompt 模板须具有稳定 `prompt_id`、模板版本和模板源码 SHA-256；动态 messages 另有逐调用内容及哈希。Query planner 和 Answerer 两类 LLM 调用不得混为一个用途。

## 五、运行工件与数据保护

### 本地工件布局

每个 run 独占目录，示意如下；`<run_id>` 必须唯一且只可新建：

```text
backend/data/rag/reports/
  YYYY-MM-DD/public-blog/dev/observe-v1/<run_id>/
    manifest.json
    events.jsonl
    questions/<question_id>.json
    human-review.jsonl
```

逐题文件包含版本化问题 Trace 和必要的完整本地上下文；JSONL 事件按真实发生次序追加。工件不得写 `/tmp`、系统临时目录、`backend/data/` 顶层或项目外。RAG 数据库快照与报告分开存储，绝不写入业务数据库。若存储过程需临时文件，只能在同一受控 run 目录内创建并原子替换。

### 隐私、访问和保留

- 离线完整 query、候选正文、最终上下文、Answerer messages 和答案均视为可能含敏感内容；只写入项目本地、被 `.gitignore` 忽略的评测报告目录。
- 新 run 使用用户私有权限（目录 `0700`、文件 `0600`），不上传、不进 Git、不进入通用日志、不额外复制到其他路径。测试需检验 sink 不输出 message/evidence 正文到 logger。
- 完整内容保留期限默认为 run 完成后 30 个自然日；更短的数据要求优先。到期由数据负责人人工核验后清理；需要延长时记录批准人/理由/新到期日。实施中不做自动删除，以免误删其他实验工件。
- 仅允许稳定白名单配置；严禁存储 API key、Token、Authorization Header、全量环境变量、Provider 原始 HTTP 请求/响应头。异常使用类型与稳定错误码，清洗后如有必要记录的 message 也不得带 credential 或完整环境信息。
- 人工 reviewer 使用非敏感 ID；人工理由保持简短，不粘贴与判断无关的私密内容。

## 六、指标与验收判定

| 观察项 | 可报告内容 | 不得混淆为 |
|---|---|---|
| 候选证据 | 每 query 的候选、候选证据覆盖、candidate Recall | 最终 Answerer 看到了全部候选 |
| 最终上下文 | 真实选择顺序、排除原因、实际 messages/hash | 候选命中即代表已提供给模型 |
| Judge 状态 | `supported`、`insufficient`、`no_results`、reason/coverage | 答案正确、完整或被证据语义支持 |
| 引用校验 | ID 是否在白名单、标签是否映射到真实 citation | 引用内容足以证明整段答案 |
| 人工质量 | correctness、completeness、groundedness、citation fidelity 分项与复核数 | 由自动状态或未复核样本推出的质量分 |
| 耗时/执行 | 各阶段及端到端延迟、失败/尝试数 | LLM/provider 费用或传输层重试（未观测则记未知） |
| 完整性 | schema、事件链、文件摘要、运行前后 snapshot 指纹 | 内容天然真实或模型结果可复现 |

完成门槛：目标 `dev` 题集逐题具备成功、跳过或失败状态；候选至最终上下文和引用链可追踪；LLM 接口 messages 与送入 fake/真实 client 的值逐字段一致且哈希通过；错误不被吞成空结果；运行快照未变化；所有受控工件路径、manifest 与 hash 校验通过；人工质量未复核项明确标 `not_reviewed`；在线默认不产生内容文件。任何一个条件失败，run 标 `incomplete`，不报告“完整审计通过”。

## 七、风险与约束

1. **内容泄漏风险：** 完整 prompt/上下文含用户输入和语料正文。以仅本地忽略目录、最小权限、白名单配置、固定留存和不打内容日志控制；在线落盘不在本期。
2. **记录边界误解：** LLMClient 入参并非 Provider 网络 payload。工件 schema 和评测说明需重复标注接口边界；不伪称捕获服务端实际收包内容。
3. **Trace 改变业务行为：** 可选 observer 的写入异常可能中断离线任务，但不得改变答案逻辑；线上默认不注入 sink。离线 sink 异常必须显式标记 run 失败，不静默丢数据。
4. **状态语义混淆：** 候选、selected evidence、LLM context、citation 和人工支撑为不同事实层；分别保存，不根据 `supported` 推导质量。
5. **报告伪完整：** 部分运行、LLM 异常、artifact 截断及快照变化均设为 incomplete；仅记录真实采集的尝试，不推断 provider 内部 retry/cost。
6. **评测准入污染：** 只运行 dev，不读取 test、不创建 candidate；Observe 完成不能关闭 `blog-formal-014` 阻塞，也不能改变 RAG 产品质量验收状态。Benchmark 工程实现是否启动按《RAG完成后Benchmark实施计划》单独判断。

## 八、明确禁止的操作

- 不实现或开启在线内容持久化，不调用外部 Observe 平台。
- 不查看或运行 `test` split，不生成或登记候选策略；不得把 Observe 工件完整性解释为 Benchmark 或 RAG 质量通过。
- 不修改、初始化、迁移或写入 `backend/data/agent.db`、`backend/data/knowledge.db`。
- 不把 RAG 数据库或报告写入 `/tmp`、系统临时目录、项目外路径或 Git。
- 不用 `supported`、引用白名单有效、候选 Recall 或 Trace 完整性代替人工语义质量复核。
- 未经单独授权不执行真实外部模型调用；开始 dev 复验前需确认预算、快照和唯一输出 run 路径。
