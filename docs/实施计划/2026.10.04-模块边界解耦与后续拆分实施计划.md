## 阶段一：完成 Writing 证据 DTO 解耦

### 目标

使 Writing 生产代码使用自身的 `WritingCitation`，不再以 `knowledge.service.CitationSnapshot` 作为 Writing 内部类型；研究端口的返回契约应显式表达引用字段，不依赖 `object` 上未声明的 `model_dump()` 方法。

### 任务

1. **核对并锁定现有改动**
   - 检查 `WritingCitation`、`ResearchBundle`、`WritingResearcher`、`WritingService` 及其未提交测试改动。
   - 搜索 Writing 生产代码中对 `CitationSnapshot` 的 import、类型注解和构造调用，形成迁移清单。
   - 运行当前目标测试作为阶段基线；记录已有失败，不将环境或既有失败归因于本阶段。

2. **明确研究端口引用契约**
   - 为 `WritingResearchResult.citations` 定义具体的 Protocol 或不可变 DTO 类型，替代 `list[object]`。
   - 保证 `WritingResearcher` 只调用契约明确支持的字段/转换，不通过未声明的 duck-typing 假设成功。
   - Fake research service 只需实现端口，不应构造完整 `KnowledgeService` 或 SQLite。

3. **统一 Writing 内部引用类型**
   - 将 research/service/execution 的内部引用统一转换为 `WritingCitation`。
   - 保持旧数据反序列化、引用字段校验、API 输出、草稿/大纲上下文和持久化序列化兼容。
   - 如旧转换辅助方法暂时仍被外部调用，保留薄兼容入口，并为后续删除标注调用方迁移条件。

4. **补齐并运行阶段验证**
   - 覆盖 Citation DTO 校验、Knowledge 边界字段转换、研究端口 fake、旧 ResearchBundle 数据解析。
   - 运行 `test_writing_citation_models.py`、`test_writing_research.py`、`test_writing_executor.py`、`test_writing_execution_repository.py`、`test_writing_execution_api.py`、`test_writing_full_flow.py`，以及改动直接涉及的其他 Writing 目标测试。
   - 在 `backend` 目录运行目标文件 `compileall`；随后执行 `git diff --check`。

### 阶段验收与停止点

- Writing 生产代码不再把 Knowledge 内部 `CitationSnapshot` 当作内部模型或持久化类型。
- Research port 的返回类型与 `WritingResearcher` 的实际消费方式一致；无需真实 Knowledge Service 即可单测 Writing Research。
- Writing 引用相关目标测试通过，API/持久化输出兼容性有断言支撑。
- 未满足以上条件前，不开始阶段二；不得借此阶段拆分 Writing executor 或 execution repository。

## 阶段二：建立 Knowledge 查询端口并收敛组合根

### 进入条件

阶段一验收通过；Writing 引用边界稳定，且当前 `pipeline_factory` 行为已有目标测试覆盖。

### 目标

令组合根统一承接 Knowledge 配置与组件构造；在线问答、Writing Research 和只读工具依赖各自最小能力接口/适配器，而非相互暴露具体服务的内部配置。避免为追求实例数减少而把不同用途强行合并成一个厚接口。

### 任务

1. **盘点实际调用能力**
   - 对 `backend/app/api/knowledge.py`、`backend/app/writing/research.py`、`backend/app/tools/search_knowledge.py`、`read_knowledge.py` 及 `dependencies.py` 的调用做逐项清单。
   - 从实际调用推导在线问答、写作检索、工具查询最小方法和结果字段；不先抽象未被使用的接口。

2. **定义端口与边界结果类型**
   - 在线问答保留现有 API 所需方法和响应类型。
   - Writing Research 复用阶段一已稳定的 DTO/port 契约，不暴露 `KnowledgeService` 内部 pipeline。
   - Tools 保持只读、限制结果大小和现有拒绝/失败关闭语义。
   - 若多个消费者共享查询结果，使用显式 DTO 或 adapter 转换；不让 Observability 或 Writing 直接依赖 Knowledge 阶段内部模型。

3. **收敛 factory 与依赖注入**
   - 在 `pipeline_factory.py` 统一 runtime config 到在线和 retrieval 能力的构造，配置值只从一个配置对象派生。
   - `dependencies.py` 仅选择并注入实现，不手工复制 embedding、pipeline、fallback 等配置字段。
   - 保留 `build_knowledge_service()` 等既有公开入口作为兼容 facade，直到全仓调用点迁移且测试验证完成。

4. **按消费者迁移并验证**
   - 先迁移 Writing Research，再迁移 Tools 或 API adapter；每个消费者单独测试并保持可替换 fake。
   - 更新 application 组装测试，使其验证注入结果和外部行为，不把 `pipeline is None` 等实现细节作为唯一契约。
   - 运行 `test_knowledge_pipeline_factory.py`、`test_application.py`、`test_knowledge_api.py`、`test_writing_research.py`、`test_writing_research_integration.py`、`test_knowledge_tools.py` 及直接受影响测试；必要时运行相关模块编译检查和 `git diff --check`。

### 阶段验收与停止点

- Knowledge 配置由 factory/config 单一构造路径派生，组合根不重复装配内部字段。
- Writing 和 Tools 可通过最小 fake/adapter 测试，不需启动完整在线服务。
- 在线 API JSON、Writing 检索 mode/limit/fallback、Tools 只读限制与既有检索排序保持不变。
- 兼容入口在迁移完成前保留；本阶段不拆 `KnowledgeService` 内部 pipeline，也不改 Repository SQL/检索算法。

## 阶段三：拆分 AgentRuntime 的状态存储与执行循环

### 进入条件

阶段二验收通过；Knowledge 工具依赖的能力接口稳定。开始前先阅读 `runtime.py`、`context.py`、`sessions/repository.py` 和现有 runtime/repository 测试，明确事件与 checkpoint 的当前顺序。

### 目标

将 SQLite 状态持久化和 Agent 单轮/多轮决策循环分开，同时让 `AgentRuntime` 继续保持现有恢复、API 调用和端到端兼容职责。

### 任务

1. **锁定行为基线**
   - 记录 run 创建、user/assistant/tool 事件、checkpoint、终态更新的顺序和 payload 字段。
   - 为 resume、checkpoint、terminal run、tool failure、loop/tool/time budget 行为补足精确断言；复用已有覆盖，避免重复或过度快照。
   - 运行 `test_runtime.py`、`test_repository.py` 作为基线。

2. **抽取 RunStateStore Protocol**
   - 定义 Runtime 所需的最小异步读写操作：run/session 读取、checkpoint 读写、事件追加/读取、状态更新。
   - 由既有 SessionRepository 适配该协议；保持 schema、事务、sequence 约束和现有公开方法不变。
   - 使用 fake store 测试协议消费，避免 loop 单测创建 SQLite。

3. **抽取纯 AgentLoop**
   - 将 LLM 请求、工具调用决策、预算判断、事件/下一状态生成移至不直接读写数据库的组件。
   - 输入状态、消息、LLM、工具和 policy/config；输出可持久化事件、下一状态与终止结果。
   - 不改变工具权限、预算上限、超时处理、错误码和敏感数据过滤。

4. **让 AgentRuntime 委托并保留兼容 facade**
   - Runtime 负责恢复 checkpoint/history、组装 loop 输入、持久化 loop 输出及终态。
   - 按原顺序落盘事件；对恢复旧 checkpoint 的缺省字段和历史事件转换保持兼容。
   - 不在此阶段改变 ContextManager 的压缩策略或 session 数据模型。

5. **运行阶段回归**
   - 新增/运行 AgentLoop 单元测试：正常完成、tool call、tool failure、各类预算耗尽及 pause/clarification。
   - 运行 `test_runtime.py`、`test_repository.py`、`test_context.py`、`test_knowledge_tools.py` 及直接受影响的 API/集成目标测试；执行相关目录 `compileall` 和 `git diff --check`。

### 阶段验收与停止点

- AgentLoop 单测无需初始化 SessionRepository/SQLite。
- AgentRuntime 仍可恢复旧 checkpoint 并保持公开调用行为。
- 事件类型、sequence、顺序和 payload 兼容；terminal run 仍不可恢复。
- 预算、安全策略和失败关闭行为均有目标测试保护；不修改 Sessions 表结构。

## 后续候选阶段（本计划不自动授权开始）

以下模块独立性较强，需以前述边界稳定为前提；每项开始时另行核对源码、输出契约并建立独立可验收切片。

1. **Knowledge 在线 Service**：保持 facade，先抽 pipeline runner，再拆 answer composition 和 observation adapter；锁定 API/pipeline/fallback 结果。
2. **Evaluation/Benchmark**：先为现有 JSON/Markdown 报告建立 schema fixtures，再分离纯指标、runner、CLI 和报告 writer；所有快照与报告遵守 RAG 路径约束。
3. **Observability**：先稳定通用事件 DTO，再拆 trace validation/redaction/aggregate、sink writer/finalizer/reader；敏感字段拒绝测试不可回退。
4. **Writing execution repository**：在 Writing 状态规则和 DTO 边界稳定后再拆任务状态、attempt、事件/幂等适配器；保持表、事务、并发版本和恢复行为。
5. **前端 API 与状态容器**：待后端 DTO/错误契约稳定后拆分 API modules、页面容器和 Writing hook；保留现有请求重试及错误解析行为。

## 通用风险与验证矩阵

| 风险 | 控制方式 | 直接验证 |
|---|---|---|
| DTO 转换改变 Writing 引用或旧任务反序列化 | 边界转换显式化，保留字段与旧数据 fixture | Citation、research、executor、repository、API、full-flow 测试 |
| Knowledge adapter 改变排序/fallback | 先锁定 pipeline/retrieval 结果，factory 只移动构造职责 | Knowledge pipeline factory、API、Writing research、Tools 测试 |
| AgentRuntime 拆分改变恢复事件顺序 | 先固化事件序列和 checkpoint 行为，再委托 loop/store | Runtime、repository、context 与集成测试 |
| 端口抽象扩大或泄露内部模型 | 仅按消费者实际调用定义最小 Protocol/DTO | fake adapter 单测及生产代码 import 搜索 |
| RAG 验证污染业务数据或产物不可复现 | 使用独立快照和规定目录，保留 fingerprint/provenance | 核对 CLI 路径、报告路径和只读数据库连接参数 |
