# 其他模块结构问题审计与后续拆分计划（计划日期：2026-10-04）

> 本文是对 `main.py` 入口装配重构之后的结构审计与后续实施计划。本次只记录问题、边界和拆分顺序，不直接修改业务代码。

## 目标

记录当前后端及前端主要模块中已确认的职责聚合、跨层耦合和测试隔离问题，为后续小步重构提供可执行的任务边界；保持现有 API、数据库格式、RAG 产物路径和 Agent 安全约束不变。

## 审计范围与方法

- 后端：`backend/app/knowledge/`、`backend/app/writing/`、`backend/app/agent/`、`backend/app/observability/`、`backend/app/llm/`、`backend/app/tools/`、`backend/app/dependencies.py`。
- 前端：`frontend/src/main.tsx`、`frontend/src/api.ts`、`frontend/src/components/`。
- 证据：源码职责、模块导入关系、文件规模、现有测试构造方式；不以文件行数单独作为拆分依据。
- 约束：优先保持行为不变；每个拆分切片必须有目标测试；不得把 RAG 实验数据库/报告写入业务数据库或系统临时目录。

## 总体判断

当前代码已经形成若干相对清晰的领域目录，但边界主要靠模块命名而不是稳定接口维持。最明显的问题不是路由层，而是离线评测、在线 Knowledge 服务、写作执行、Agent Runtime 和 Observability 之间共享了较多内部模型与构造细节。若继续直接在现有大文件中叠加功能，测试会越来越依赖完整组合根或真实 SQLite 初始化，故后续应以“先建立接口边界，再搬迁实现”为主。

## 已确认问题

### P0：组合根仍重复构造 Knowledge 服务，配置语义容易漂移

**证据**

- `backend/app/dependencies.py` 的 `build_app_dependencies()` 先通过 `create_knowledge_service()` 构造带 pipeline 的在线服务。
- 同一函数随后又以该服务的 embedding 参数重新构造 `writing_research_service = KnowledgeService(...)`，但显式设置 `pipeline=None`。
- `knowledge_service`、`writing_research_service`、工具层的 `KnowledgeRepository` 同时被注入不同业务路径。

**影响**

- Knowledge API 与 Writing Research 的检索能力、fallback 和配置来源不再由单一接口表达。
- 新增 Knowledge 配置时容易只更新其中一个构造路径；测试必须理解组合根的内部构造才能替换依赖。

**建议**

1. 先定义 `KnowledgeQueryPort`/研究专用查询接口，明确在线问答、写作研究和只读工具需要的最小能力。
2. 将 pipeline 创建与基础检索配置封装到独立 factory/config 对象；组合根只选择实现，不复制字段。
3. 为 API、Writing、Tools 分别保留薄适配器，完成迁移后再删除重复构造路径。

### P1：Knowledge 在线服务聚合过多阶段逻辑

**证据**

- `backend/app/knowledge/service.py` 约 899 行，同时包含 query planning、candidate retrieval、reranking、evidence selection、answerability、LLM answer、观察事件和响应模型/快照相关逻辑。
- 该服务直接依赖 `RecordingLLMClient` 和 `app.observability` 的 prompt identity/录制边界，而不是只接收一个抽象的观察接口。

**影响**

- 在线请求流程、证据决策、模型回答和离线观察难以独立测试。
- 任一阶段的配置或事件字段变化都可能影响整个 Service 的回归范围。

**建议拆分顺序**

1. 保持 `KnowledgeService` 外部方法不变，先抽取 `KnowledgePipelineRunner`，只负责阶段顺序、阶段状态和错误映射。
2. 抽取 `AnswerComposer`，输入最终证据和问题，输出答案/引用；通过协议接入 LLM 与录制器。
3. 抽取 `KnowledgeObservationAdapter`，将内部阶段结果映射为观察事件。
4. 最后再按公共模型/端口整理 `pipeline_models.py`，避免先移动类型导致大量无目的 import 变化。

### P1：离线评测入口是 CLI、运行器和指标计算的单体

**证据**

- `backend/app/knowledge/evaluation.py` 约 1507 行，承担命令行参数、数据集读取、数据库访问、检索执行、答案评估、报告生成和状态记录。
- `backend/app/knowledge/benchmark.py` 又同时负责 benchmark CLI、只读快照打开、指纹、策略执行和报告落盘；通过 `benchmark_compare.py` 承担比较输出。

**影响**

- 离线评测逻辑难以复用于 API/脚本而不引入 CLI 和文件系统副作用。
- 单元测试需要构造完整数据库/manifest，指标变更和存储格式变更互相牵连。

**建议拆分顺序**

1. 把 `evaluation.py` 的纯数据结构、问题读取/校验、检索评估、报告序列化分别建立内部模块。
2. 令 CLI 只负责参数解析和调用 `EvaluationRunner`，路径校验与 RAG 目录约束放在 runner 边界。
3. 令 `BenchmarkRunner` 只负责一次运行，快照 fingerprint 和 compare/report writer 保持独立。
4. 对每个报告字段建立 schema fixture，保证旧 JSON/Markdown 输出兼容。

### P1：KnowledgeRepository 每次搜索都加载完整文档、分块和向量

**证据**

- `backend/app/knowledge/repository.py` 的 `search_chunks()`、`search_vector_chunks()` 和 `search_hybrid_chunks()` 均先调用 `list_documents()`、`list_chunks()`，向量检索还调用 `list_embeddings()`，然后交给内存 Retriever。

**影响**

- Repository 同时承担 SQLite 访问和检索数据集组装；数据量增长会带来重复全表读取和内存峰值。
- 性能测试难以区分 SQL、数据映射和 Retriever 的耗时；在线服务无法声明资源边界。

**建议**

1. 先增加 `KnowledgeSnapshotReader`/批量读取端口，统一一次请求内的数据快照。
2. 将 `Repository` 的 CRUD/迁移职责与 `Retriever` 的候选计算职责分离。
3. 在不改变结果排序的前提下增加查询耗时、读取数量和候选数量测试；暂不直接改 SQL 索引或结果算法。

### P1：Writing 执行器与执行 Repository 形成厚边界

**证据**

- `backend/app/writing/executor.py` 约 288 行，编排 research、outline、draft、attempt 状态和错误处理。
- `backend/app/writing/execution_repository.py` 约 461 行，既保存 attempt/事件/状态，又包含恢复、幂等和序列化细节。
- `backend/app/writing/service.py`、`repository.py`、`execution_models.py` 共同依赖 `knowledge.service.CitationSnapshot`，Writing 对 Knowledge 的内部快照模型形成反向耦合。

**影响**

- 状态机规则、执行生命周期、数据库持久化和模型输出校验的变更会同时触及多个大模块。
- 将来替换研究实现或执行存储时，必须携带 Knowledge 的内部类型和 SQLite 细节。

**建议拆分顺序**

1. 建立 Writing 自有的 `CitationReference`/证据 DTO，在边界处转换 `CitationSnapshot`。
2. 抽取纯状态机 `WritingWorkflow`，只接收当前任务和命令，输出合法 transition。
3. 将 executor 收敛为 orchestration：调用 research/outline/draft ports，并把 attempt 读写交给 repository port。
4. 将 `execution_repository.py` 拆为任务状态、attempt 记录、事件/幂等三个可测试适配器；保持现有表和 API 不变。

### P1：AgentRuntime 同时负责恢复、上下文、工具循环和持久化

**证据**

- `backend/app/agent/runtime.py` 约 511 行，包含 run 创建/恢复、checkpoint 恢复、历史事件转消息、LLM loop、tool call、预算/超时、事件写入和最终状态。
- `backend/app/agent/context.py` 约 238 行，同时处理消息上下文、压缩/截断和状态恢复辅助逻辑。

**影响**

- Agent 行为测试需要同时准备 SessionRepository、ToolRegistry、LLM fake 和 checkpoint 数据。
- 恢复语义与一次性执行语义耦合，未来替换存储或增加后台执行时风险较高。

**建议拆分顺序**

1. 先抽取 `RunStateStore` 协议，封装 SessionRepository 的 run/checkpoint/event 读写。
2. 抽取纯 `AgentLoop`，输入状态、LLM、工具和 policy，输出事件/下一状态，不直接写数据库。
3. 由 `AgentRuntime` 保留恢复、持久化和端到端兼容包装。
4. 为 loop、resume、terminal run、tool failure 分别建立测试，确保状态序列和错误码不变。

### P2：Harness/Autonomous Research 的安全策略和领域研究编排仍相互嵌套

**证据**

- `backend/app/agent/harness.py` 依赖 `ToolRegistry` 并负责预算、调用、审计和执行状态。
- `backend/app/writing/autonomous_research.py` 在单个研究方法中创建工具包装、capturing LLM、strategy、Harness、Budget、ToolPolicy，并维护证据字典。

**影响**

- 研究策略无法在不启动 Harness 的情况下单测；Harness 的通用边界被 Writing 的证据模型和只读工具语义污染。
- 安全规则、预算规则和证据收集规则的失败原因容易混在一起。

**建议**

- 保持 Harness 只处理通用执行契约；抽取 `ResearchToolAdapter`、`EvidenceCollector` 和 `ResearchStrategy` 的组装层。
- 先补充契约测试，再移动代码；不得放宽当前只读工具、预算和 fail-closed 约束。

### P2：Observability 录制和落盘模块过厚，并直接依赖业务模型

**证据**

- `backend/app/observability/rag_trace.py` 约 520 行，包含 schema、敏感字段检测、JSON 校验、hash、时间和 trace 模型。
- `backend/app/observability/rag_trace_sink.py` 约 764 行，包含 trace 聚合、SQLite/file sink、状态更新和报告查询。
- `recording_llm_client.py` 约 410 行，同时包装 LLM、构造 prompt identity、记录调用和截断响应。
- `recording_reranker.py` 直接依赖 `knowledge.pipeline_models.CandidateEvidence`，观察层知道 Knowledge 内部候选模型。

**影响**

- 观察 schema、业务阶段和持久化后端无法独立演进。
- 录制器测试覆盖了大量 provider/业务模型组合，敏感数据规则变更的回归面较大。

**建议拆分顺序**

1. 将 `rag_trace.py` 拆为 schema/value validation、redaction/hash、trace aggregate 三层，但先保持公开导出。
2. 将 Sink 拆为 append-only writer、run finalizer、query/report reader；文件和 SQLite 实现共享端口。
3. 让 recording wrappers 接收通用事件 DTO，Knowledge 阶段通过 adapter 转换，移除对 `CandidateEvidence` 的直接依赖。

### P2：LLM 客户端协议、预算包装和录制包装缺少清晰层次

**证据**

- `backend/app/llm/compatible_client.py` 直接实现 Agent 的 `LLMClient` 协议。
- `backend/app/llm/budgeted_client.py`、`observability/recording_llm_client.py` 都以 wrapper 形式包裹同一协议，但组合顺序由调用方决定。
- `dependencies.py` 直接创建 provider client，业务模块通过具体 `LLMResponse`/`Message` 类型沟通。

**影响**

- timeout、预算、记录、provider 错误的责任边界不明确，包装顺序改变可能改变错误/usage 语义。

**建议**

- 定义 provider response 与 Agent response 的最小转换边界；为 wrapper 规定顺序和错误传播契约。
- 在组合根集中构造 wrapper chain，并增加“预算先于 provider / 记录不泄露敏感字段”的契约测试。

### P2：前端入口组件和 API 模块承载多个页面/协议职责

**证据**

- `frontend/src/main.tsx` 同时管理 session、对话消息、Knowledge capability/document、请求状态、错误状态、模式切换和 WritingPanel 装配。
- `frontend/src/api.ts` 约 231 行，集中包含 session、knowledge、writing 的类型、请求重试/错误解析和所有 endpoint 函数。
- `frontend/src/components/WritingPanel.tsx` 约 271 行，包含写作任务状态机的加载、提交、轮询/刷新、错误和展示状态。

**影响**

- 页面级状态变化会影响入口组件和跨域 API 类型；前端测试难以针对单一流程隔离。
- API 错误语义和业务 DTO 共享一个文件，后续接口变更容易造成无关组件编译耦合。

**建议拆分顺序**

1. 将 `api.ts` 按 `sessions.ts`、`knowledge.ts`、`writing.ts` 拆分，公共 HTTP client/error parser 单独保留。
2. 将 `main.tsx` 拆为 Chat/Knowledge 页面容器和 session hook；保持当前路由/构建入口。
3. 将 WritingPanel 的请求状态提取为 `useWritingTask`，组件只负责交互和展示。
4. 以 `tsc`/现有前端构建和人工 API mock 核对作为每步验证。

## 暂不列为立即重构项

- `tools/` 目录目前工具数量少、注册边界清晰；先不按工具类型拆目录。
- `sessions/repository.py` 虽然承担多个 Session 相关表操作，但它是当前 AgentRuntime 的持久化边界；应随 RunStateStore 抽取，不单独先改。
- `main.py` 兼容导出清理属于上一项重构的收尾，不与本审计中的领域拆分混合实施。

## 推荐实施顺序

1. **组合根与 Knowledge 端口**：消除重复构造，建立最小接口；风险低、能改善后续测试隔离。
2. **Writing 证据 DTO 与状态机**：切断跨领域内部模型依赖，再拆执行仓储。
3. **Agent Loop / RunStateStore**：拆持久化与纯执行循环，保持 runtime 作为兼容 facade。
4. **Knowledge 在线服务**：按 pipeline、answer、observation 拆分，基于前两步稳定的端口实施。
5. **离线 Evaluation/Benchmark**：以输出 schema fixture 锁定报告兼容性后拆 CLI 和 runner。
6. **Observability**：最后拆 schema/sink/wrapper，避免在业务边界尚未稳定时反复改事件适配。
7. **前端 API 与状态容器**：后端 DTO/错误契约稳定后再拆，减少前后端同时漂移。

## 通用实施要求

每个后续切片均应遵循以下门禁：

1. 先补充或迁移直接相关的单元/集成测试，再做最小代码移动。
2. 保留旧公开 import、HTTP JSON、数据库表和报告字段，确认调用方迁移后再删除兼容层。
3. RAG 验证使用 `backend/data/rag/databases/` 和 `backend/data/rag/reports/` 下的独立快照及报告路径。
4. 运行目标测试、相关模块 `compileall` 或前端类型/构建检查；不以全量测试替代领域测试。
5. 每个阶段完成后更新当日开发日志，记录问题、处理方式和验证结果。

## 风险与验证矩阵

| 风险 | 控制方式 | 直接验证 |
|---|---|---|
| 拆分改变检索排序或 fallback | 先锁定候选/证据 fixture，保留旧 service facade | Knowledge API、pipeline、RAG 目标测试 |
| 写作状态迁移破坏幂等/并发控制 | 先抽纯 transition，保留 repository SQL 和 version 检查 | `test_writing_workflow.py`、`test_writing_full_flow.py` |
| Runtime 恢复事件顺序变化 | 对 checkpoint、resume、terminal run 建立事件序列断言 | Agent runtime/session 目标测试 |
| 观察数据泄露或 schema 漂移 | 保留敏感字段拒绝测试和 schema fixture | trace/recording/sink 目标测试 |
| 离线报告不可复现 | 固定 manifest、snapshot fingerprint 和输出 schema | evaluation/benchmark 目标测试 |
| 前端接口拆分造成请求行为变化 | 保留公共 HTTP client 与错误解析测试，执行类型检查/构建 | frontend `tsc`/Vite build |

## 本次审计结论

当前最值得优先处理的是 `dependencies.py` 的重复 Knowledge 构造、Writing 对 Knowledge 内部快照的依赖，以及 AgentRuntime 的持久化/执行循环耦合。Knowledge 离线评测和 Observability 虽然文件最大，但应在接口和输出契约补齐后再拆，避免仅按行数进行高风险搬迁。
