# Agent Runtime Tracing 系统实施计划

> 状态：审阅稿。本文根据 2026-11-20 已确认的架构讨论编写；尚未开始实现。计划中的建议参数需经审阅后冻结。

## 目标与范围

为 Python Agent Runtime 建立平台中立的结构化 Trace 生产能力，并由桌面 Rust 宿主通过本机接口消费、持久化和按期清理。Trace 用于本地运行诊断，不承担业务状态、审计或 Eval 数据集职责。

本计划只覆盖当前 Agent Runtime 的 Trace 采集与桌面落盘，不实现 Trace 查看界面、外部观测平台、Eval runner、完整 Prompt/响应记录，也不要求引擎崩溃后恢复尚未被 Rust 消费的内存记录。

## 已确认约束

- Python Runtime 生产 Trace；Rust 桌面端消费并负责持久化。数据格式不绑定 Windows/Tauri，后续其他宿主可实现同一消费契约。
- Python 使用有界环形缓冲区。缓冲区满时覆盖最旧记录，并暴露丢弃统计。
- Rust 将 Trace 落盘到应用数据目录的日志块，保留 30 天；暂不提供用户查看、管理或导出接口。
- Trace 与现有 Run Events 分离，通过 `run_id` 关联；Run Events 继续承载业务进度。
- 日常 Trace 不保存用户原文、Prompt、模型回答、工具参数或工具返回正文；不保存绝对路径、凭据、环境变量。
- 异常只保存稳定错误码和分类，不保存原始异常文本。
- Trace 是诊断数据。Python 引擎退出时，尚未被 Rust 消费的缓冲记录允许丢失；Rust 必须记录可识别的序号缺口和丢弃统计。

## 建议的首期契约

每条记录表示一个已完成的 Span，采用 JSON 对象并按行传输，`schema_version` 固定为 `runtime-trace/v1`。字段建议为：

| 字段 | 含义 |
|---|---|
| `event_id` | 稳定唯一事件 ID，用于消费端幂等去重。 |
| `runtime_instance_id` | 每次 Python 引擎进程启动时新建的 UUID；不得复用可跨重启保留的 `service_instance_id`。 |
| `sequence` | 实例内严格递增的序号；缓冲覆盖后允许出现可检测缺口。 |
| `trace_id`、`span_id`、`parent_span_id` | 一次 Run 的 Trace 及 Span 父子关系。 |
| `run_id` | 关联现有 Run；不额外写入用户消息或 Session 内容。 |
| `operation` | 固定操作名，例如 `run.execute`、`model.complete`、`tool.execute`、`memory.recall`、`knowledge.search`、`validation.run`。 |
| `started_at`、`duration_ms` | UTC 开始时间及由单调时钟测得的耗时。 |
| `status` | `ok`、`error`、`cancelled` 或 `timeout`。 |
| `error_code`、`error_category` | 失败时的稳定分类；无失败时为空。 |
| `attributes` | 经白名单验证的非正文属性，例如 Provider/模型名、工具名、重试次数、返回条数、usage 数值。 |

属性采用白名单和严格长度/类型限制，不允许任意字典透传。Span 上下文通过 Python `ContextVar` 传播，异步子调用自动继承 `trace_id` 和父 Span。Trace 写入和 HTTP 读取都不得等待磁盘操作。

| 路径 | 职责 |

| `backend/tests/test_runtime_trace_buffer.py` | 并发追加、游标读取、覆盖和丢弃统计测试。 |
| `backend/tests/test_runtime_trace_api.py` | 认证、分页、实例隔离及错误响应测试。 |

## 分阶段执行

### 阶段 0：冻结首期参数与边界

1. 审定 Trace v1 字段、操作名和属性白名单；实现前拒绝未声明字段。
2. 审定环形容量、接口分页上限、Rust 拉取间隔及断线退避策略。
3. 审定日志块路径与切分方式，并定义 30 天清理按文件时间还是记录时间计算。
4. 确认首批插桩位置：Run 总体、模型调用、工具调用、记忆/知识检索及验证步骤。

建议初值供审阅：Python 环形容量 4096 条、单次最多读取 500 条、Rust 活跃引擎每秒拉取一次；日志以 UTC 日期分块为 JSONL，Rust 串行写入。运行量测后再调容量/轮询，不改变协议语义。

### 阶段 1：Python Trace 契约与缓冲区

1. 先为 v1 模型编写测试，验证必需字段、固定状态值、属性类型/长度和敏感字段拒绝。
2. 实现按 `runtime_instance_id + sequence` 排序的有界环形缓冲区；覆盖最旧记录时递增丢弃计数。
3. 提供线程安全的非阻塞追加和 `read_after(cursor, limit)` 快照读取；响应包含 `items`、`next_cursor`、`dropped_total`、`oldest_sequence` 和 `runtime_instance_id`。每个引擎进程启动时创建新的 `runtime_instance_id`，序号从 1 开始。
4. 覆盖并发生产/读取、容量边界、跨实例重启、消费者落后导致序号缺口等行为。

### 阶段 2：Runtime 插桩与桌面读取接口

1. 为 Span 上下文实现同步/异步上下文管理器，使用单调时钟计时，并确保异常转换成稳定错误码/分类后仍按原逻辑传播。
2. 接入 Run 生命周期、模型网关、Harness 工具调用、记忆/知识检索和验证边界；禁止在事件属性中传入请求正文或原始异常对象。
3. 新增桌面专用 `GET /api/desktop/traces?after=<sequence>&limit=<n>`。沿用本机 Bearer token 与实例校验，并要求已 attach 的 `X-Tomato-Client`；拒绝超范围分页参数。
4. 测试接口认证、游标边界、空缓冲区、覆盖后的缺口描述、属性不含敏感正文，以及 Trace 错误不改变 Agent Run 的业务结果。

### 阶段 3：Rust 消费与落盘

1. 新建 Trace 存储模块，在 Tauri 应用数据目录的 Trace 子目录内写 UTC 日期分块 JSONL；落盘记录不混入聊天数据库或 Python 业务数据库。
2. 消费端按实例 ID 和游标拉取批次，先验证 schema/version/实例/序号，再追加 JSONL、同步文件数据并原子更新本地游标状态；写入失败时不推进游标。
3. 游标状态按 `runtime_instance_id` 分别保存。启动时扫描保留期内的 Trace 文件重建 `event_id` 去重集合，以处理日志追加成功、游标状态落盘前进程崩溃造成的重放；按实例和序号识别重复/缺口。
4. 写入错误时保留旧游标，记录本地存储错误计数并退避重试；单一 Rust 消费者按序串行落盘。
5. 在引擎启动后运行消费者，在引擎停止或桌面退出时停止轮询；若引擎重启，使用新进程实例 ID 和新游标空间继续消费。
6. 清理超过 30 天的受管日志块；只处理 Trace 目录下符合命名规则的普通文件，不跟随符号链接，不触碰其他日志或用户数据。

### 阶段 4：跨边界验证

1. Python API 集成测试使用固定假 Span，验证分页和覆盖统计，不调用真实 Provider。
2. Rust 单元测试使用临时目录和本地假 HTTP 服务，验证批量写入、日志/游标间崩溃后的重放去重、写盘失败不推进游标、实例重启和 30 天清理。
3. 端到端验收启动真实 Python 引擎和桌面 Rust 消费端，执行一个合成 Run，验证 `run_id` 关联、Span 父子关系、日志文件可解析和消费者游标推进。
4. 验证故障边界：消费者暂停时 Python 覆盖旧记录可见；引擎终止时未消费记录允许缺失；Trace 写入或消费失败不阻断 Agent Run。

## 验收条件

- Runtime 关键调用能形成可关联的 Trace/Span 树，Run Events 行为保持不变。
- Trace 生产不做磁盘 I/O，不等待 Rust；环形覆盖可检测并带有丢弃计数。
- API 仅对已认证桌面连接开放，并支持稳定游标分页。
- Rust 重复拉取不会重复落盘；写入失败不会推进游标；超过 30 天的受管块按策略清理。
- 自动化测试证明正文、原始异常、凭据、环境变量和绝对路径不会进入 Trace 文件。
- Python/Rust 任一侧 Trace 组件故障均不改变任务执行、取消、恢复或业务事件结果。

## 本次审阅需确认

1. 首期是否接受建议参数：4096 条环形容量、每批 500 条、每秒轮询一次。
2. 是否接受按 UTC 日期生成 JSONL 日志块；落盘数据不使用压缩，30 天按文件日期清理。
3. Trace 消费接口是否限定桌面 attach 客户端；未来 Linux/Android 宿主复用协议并各自实现认证适配。
4. Python 环形结构是否使用线程安全的 `deque(maxlen=...)`，由异步请求直接快照读取；不另设 Trace 专用 OS 线程。若要求专用线程，需再定义线程队列和关闭/排空语义。

## 明确不包含

- 用户界面、导出/删除操作或设置项。
- Prompt/回答/工具输入输出正文采集。
- Python 侧持久化 outbox 或引擎异常后的未消费 Trace 恢复保证。
- OpenTelemetry SDK/OTLP 导出或外部观测服务接入。
- RAG 专用 Trace sink 迁移、Eval runner 建设或 Trace 自动评分。
