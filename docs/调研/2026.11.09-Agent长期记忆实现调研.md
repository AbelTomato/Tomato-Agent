## 2. CAMEL

### 2.1 基础长期记忆是历史与向量块的组合

`LongtermAgentMemory` 接收 `ChatHistoryBlock`、`VectorDBBlock` 和 ContextCreator。

- 写入：消息同时写入历史块与向量块；最新 user 文本作为当前检索主题。
- 召回：用当前主题搜索向量块，将结果与历史块返回的上下文组合。
- 向量块存储的是消息文本嵌入及完整 MemoryRecord payload，并不是先自动提取稳定偏好。
- MemoryRecord 包含 UUID、角色、时间、agent_id 和扩展元数据。
- 基础组合类的回滚只修改历史块，向量记忆保留；`clear()` 则清空两个块。因此必须区分“回退会话”和“删除长期记忆”。

持久化取决于后端配置：ChatHistoryBlock 默认使用内存存储，VectorDBBlock 默认 Qdrant 在未配置本地路径或远程地址时也使用内存。创建一个名为 LongtermAgentMemory 的对象，不自动保证重启后持久化。

当前源码的 `ScoreBasedContextCreator` 明确说明 token_limit 仅为兼容保留，不再据此筛选记录；实际按时间排序并计数。不能根据类名或旧文档推断它仍实现按重要性裁剪到预算内。

### 2.2 外部服务与工作流经验是另外两条路线

`MemantoMemory` 将 user/assistant 文本发送到外部服务，由服务完成 remember/recall。系统消息、工具元数据等仍留在本地历史。召回按原记录标签去重，插入时避免拆散工具调用与结果。清空或回滚本地会话不会清除服务端记忆。这个文件只能证明服务接入方式，不能据此推断 Memanto 服务内部如何合并冲突或管理画像。

`WorkflowMemoryManager` 则从任务对话生成结构化工作流总结，保存带元数据和版本的文件；加载时可按角色匹配或调用模型挑选相关工作流。它更接近“过程经验/SOP 记忆”，与个人偏好不同。

借鉴点：保留可替换的记忆接口；近期对话与长期召回分别提供；记录稳定来源 ID；将过程经验作为后续独立类型。个人偏好的提取、有效期与纠错仍需我们自己定义。

## 3. Cline

### 3.1 Memory Bank 是文档方法

本地文档明确将 Memory Bank 定义为 documentation methodology。用户将约定放入规则文件，要求 Agent 创建、读取和维护项目内的 Markdown：

- projectbrief.md：目标与范围。
- productContext.md：产品背景。
- activeContext.md：当前重点与决策。
- systemPatterns.md：架构和模式。
- techContext.md：技术栈与环境。
- progress.md：进展和待办。

它利用普通文件工具和规则驱动跨会话复用；在检查的核心代码路径中没有发现名为 Memory Bank 的独立事实提取、冲突消解或向量检索服务。文档中“每次任务读取全部 Memory Bank”的做法适用于小规模项目资料，个人记忆增长后应改为按需读取。

### 3.2 持久规则有真实加载链路

Rules 与 Memory Bank 本身不同。规则加载器读取全局和工作区文件，处理禁用状态；运行时将启用规则渲染到系统提示中。UI 开关会同步修改文件的 frontmatter，使文件成为启用状态的依据。

这说明“用户明确设置的行为规则”可以是一个单独的配置层。自动从聊天归纳出的历史记忆，不应直接获得相同的指令地位。

### 3.3 压缩结果与原始记录分开

SDK 有 basic 和 agentic 两种压缩策略。后者将较早内容总结，保留近期内容；溢出恢复可使用确定性的 basic 策略。

`SessionCompactionState` 保存来源消息数、来源前缀指纹和边界，以及压缩后的消息。使用摘要时先检查它是否仍对应原始前缀，再追加新消息。测试包含“原始前缀编辑后拒绝旧压缩结果”的场景。

对本项目最值得借鉴的是：会话原始记录是依据，压缩结果是带来源版本的派生视图；用户编辑历史后不能继续静默使用旧摘要。Auto Compact 解决长会话长度，Memory Bank 解决跨任务资料，两者分别管理。

## 4. LangGraph

### 4.1 明确分开两种状态

`StateGraph.compile()` 分别接收 checkpointer 与 store。

- Checkpointer：按 thread_id 管理图运行状态、消息、暂停、恢复和重放。
- Store：通过 namespace + key 访问 JSON 数据，可供多个 thread 共享。

测试中，同一个 Agent 可根据 user_id 从不同命名空间读取不同用户信息，再由应用代码把内容加入 prompt。这证明用户记忆与会话 ID 可以分离，而不是每开一个会话就复制一份个人档案。

### 4.2 Store 提供基础设施，应用决定记什么

BaseStore 提供 get、put、delete、search、命名空间列举和同步/异步接口。Item 保存结构化 value、key、namespace、创建和更新时间。

语义索引是可选的，可指定只嵌入部分字段，单条记录也可以关闭索引。结构化过滤、命名空间与向量检索可以结合。工具可通过运行时注入获取 Store，不必由模型自行传递数据库对象。

本地版本包含内存、SQLite 和 PostgreSQL 后端。InMemoryStore 退出即丢失；SQLite 后端包含结构化数据、向量表及 TTL 支持，适合参考本地优先设计。TTL 可以配置访问续期与清理，但“长期事实是否仍正确”不能只靠缓存过期规则决定。

LangGraph 不会仅因提供了 Store 就自动提取用户偏好。提取时机、schema、合并冲突、确认和画像生成需要应用层逻辑或额外组件实现。命名空间也是组织和过滤机制，调用方仍需控制允许访问的范围。

借鉴点：为个人偏好、项目记忆、历史事件建立明确作用范围；保留稳定 key 与结构化元数据；把向量索引作为检索能力，事实仍由业务记录管理。无需为了借鉴 Store 而重写 Tomato-Agent Runtime。

## 5. OpenAI Agents Python

### 5.1 Session 与长期 Memory 是独立能力

普通 Session 接口管理会话消息，SQLiteSession 等后端负责持久化。Runner 读取会话历史、合并当前输入、保存新增内容。SessionSettings 可限制最近条目，session_input_callback 可改变本轮输入的历史选择。会话压缩还有独立包装器。

这部分主要解决对话连续性。当前本地版本另外包含 SandboxAgent 的 Memory capability，文档明确称其为独立于 Session 的长期经验记忆。不能将这个仓库概括为“只有聊天历史”。同时，这套 capability 依赖 Sandbox 运行路径，不能推断普通 Agent 默认启用了它。

### 5.2 两阶段生成

运行过程中，将每个 run segment 追加到对应 conversation 的 JSONL。稳定 conversation 标识可把多次调用归到同一份来源中。

当前管理器在 sandbox session 关闭时通过 pre-stop hook 执行 flush：处理累计的 conversation 文件，再进行整合。它不是每个聊天回合结束就立即完成一轮画像更新。

第一阶段：模型为每份累计记录生成对话总结和 raw memory，保留来源、终态与证据。无有用信息时支持返回全空结果，不强制产生记忆。导出的来源排除 system、developer、reasoning 等不应进入记忆的内容；超长输入有截断标记。

第二阶段：单独的整合 Agent 读取选中的 raw memories，按需打开对话总结，维护：

- MEMORY.md：详细记忆与可检索索引。
- memory_summary.md：用户背景、偏好、通用提示和记忆导航。
- rollout_summaries/：每次对话/任务的总结与证据。
- skills/：有充分证据时可沉淀复用过程。

提取与整合模型可以分别配置。默认最多选取最近 256 份 raw memories 参与整合；存储层计算新增、保留、移除的来源，提示词要求移除失去支持的旧内容，并保留仍有其他来源支持的共同结论。选择集合变化不等于原始历史被物理删除，也不等于严格的用户级“忘记某事实”接口。

### 5.3 渐进读取与偏好证据

新 run 首先获得摘要，再按关键词查询 MEMORY.md，最后打开少量相关对话总结或技能文件。这条默认实现主要依赖文本/文件检索，没有要求向量库。

提示词对证据有具体约定：用户原话、纠正和反复要求，是偏好的主要依据；助手总结只能作为辅助；一次任务中的表达不应自动扩大为长期人格判断；不确定的结果应保留不确定性；原始 rollout 不得修改。它是“先保留证据，再跨对话归纳”的实现。

Memory 可以分别禁用读取或生成，避免临时内部任务被无差别写成长期经验。隔离依据是 memory layout 与存储环境；仅改变 Agent 名称不会自动隔离。新建空环境也不会自动拥有旧记忆，需要复用目录或恢复持久状态。

需要区分实现保证与模型约定：来源选择、文件组织和生命周期由代码执行；哪些结论应合并、怎样消解过期信息，大量依赖整合提示词和模型质量。它不等于已经具备适合个人产品的事实级审计、确认 UI 和确定性删除闭环。

## 6. 对 Tomato-Agent 的建议

### 6.1 保留四类不同职责

1. 原始证据：现有会话消息、必要的执行结果与来源快照。
2. 长期事实：偏好、习惯、背景、事件，带作用范围、来源、版本和有效状态。
3. 派生视图：精简用户摘要、主题总结、检索索引，可以重建。
4. 运行上下文：本轮问题、近期消息、当前任务状态与预算内召回内容。

明确的用户行为设置单独管理；自动提取的记忆作为历史数据提供，不因为持久化就获得改变权限或覆盖当前要求的能力。

### 6.2 先事实，再摘要

候选链路：原始消息 → 提取候选事实及证据 → 校验来源和作用范围 → 判断新增/重复/替代/冲突 → 保存事实版本 → 更新索引和摘要。

用户明确要求记住或纠正的信息应能立即生效。普通对话可以后台批量提取；不能只依赖退出应用时刷新，否则常驻桌面进程中的新偏好长时间不可用。提取与整合任务需要持久化进度、幂等和重试；不能假设进程内队列已经提供崩溃恢复。

“用户说过”与“用户现在仍然如此”应分开；明确陈述与模型推断应分开；重复引用同一条来源不能当作多次独立证据。

### 6.3 复用 RAG 的检索能力

保留知识检索与个人记忆检索的业务区别，共用嵌入、关键词/向量混合、重排、观察和评测基础。

个人记忆检索前先限制个人/项目/会话范围及生效状态，再做相关性排序。对当前问题有用的少量核心偏好可直接提供；具体背景和事件按需召回；需要核查时读取来源原文。不同来源分数不可直接混加，统一组装时做去重和长度预算。

现有知识库主要以 Document/Chunk 为中心，不建议把全部记忆直接伪装成普通文档后复用整条知识问答链。个人事实的作用范围、替代关系和短文本特点需要独立适配。

### 6.4 存储建议

SQLite 管理事实、版本、证据关系和处理进度；检索索引与主题摘要是派生数据。提供可读的“助手记住了什么”界面，支持按条查看来源、编辑、撤销和导出 Markdown。

如果支持直接编辑导出文件，需要规定如何导入和解决版本冲突；首期可先做只读导出，避免数据库与 Markdown 同时成为可独立修改的依据。

“忘记”应覆盖事实、向量索引、摘要和缓存，并处理旧来源再次提取的问题。聊天删除与记忆删除可分别控制，但必须让用户理解两者关系。

### 6.5 建议的第一期验收

- 明确保存偏好后，新会话可使用，并显示原始依据。
- 一次性任务要求不变成全局偏好。
- 用户纠正后旧事实退出正常召回，保留可解释的替代关系。
- “最近学 Rust”不会自动变成“精通 Rust”。
- 项目约束不会串到其他项目或个人全局。
- 忘记后，摘要和向量均不继续使用，也不从同一旧来源自动复活。
- 原始消息变化时旧摘要失效，最新问题始终进入模型请求。
- 后台提取中断可以恢复，重复处理不会重复计为新证据。

## 7. 后续需要共同确定的产品选择

- 自动记忆：明确保存、自动候选、自动生效各覆盖哪些类别；是否提供低打扰的集中审阅。
- 接入入口：优先 Python Agent，还是要求 Windows 原生聊天首期即可跨会话使用。
- 删除语义：忘记一条事实、删除一次会话、清空个人记忆分别影响哪些数据。

当前最适合先讨论的是写入策略与桌面接入边界。存储可先继续使用 SQLite，已有 RAG 足以支持首轮检索验证；是否需要图谱或专用向量引擎应由后续失败案例和规模决定。
